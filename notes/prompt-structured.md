# 结构化输出：让模型稳定吐出可解析的结果

只要模型输出要进程序，第一道坎就是「格式稳定」。这篇讲怎么把 JSON 输出做稳、JSON mode 和 function calling 的区别、few-shot 怎么挑、思维链什么时候有害，以及为什么「不要做什么」这类指令经常失效。

## 怎么让模型稳定输出 JSON？

按可靠性从低到高，有四层手段，通常要叠加使用：

**第一层：把结构写清楚。** 给出字段名、类型、取值范围、是否必填，最好给一个完整示例。模糊的「返回 JSON」等于没说。

**第二层：用 JSON mode / 结构化输出。** 服务商提供 `response_format={"type":"json_object"}`，约束解码过程只生成合法 JSON。注意它只保证「语法合法」，不保证「字段齐全、值正确」。

**第三层：Schema 约束解码。** 更严格的做法是按 JSON Schema 约束 token 采样（如 outlines、guidance、各家的 structured outputs）。它保证字段名和类型都对，但保证不了语义。

**第四层：应用侧容错。** 这是最容易被忽略的一层。即使前三层都做了，模型仍可能：截断（max_tokens 不够）、多一个括号、把中文引号当英文引号、在 JSON 前后加解释文字。所以解析器必须能容错：

- 剥掉 ```json 围栏；
- 括号配对扫描，找到第一个完整的对象；
- 修尾逗号、把中文引号换成英文；
- 括号失衡时用栈修复（多一个 ] 是常见错误）；
- 截断导致的完全不闭合，**老实返回失败**，不要猜——猜出来的半个对象比报错更危险。

一句话：**语法靠约束，语义靠校验，兜底靠容错。** 三层缺一层，线上就会偶发解析失败。

## JSON mode 和 function calling 有什么区别？

两者都产出结构化数据，但语义不同：

- **JSON mode**：只是「让输出是 JSON」，模型不知道自己为什么要输出这个结构。适合抽取、分类这类「一次性出结果」的场景。
- **function calling（工具调用）**：模型输出的是「我要调用哪个函数、参数是什么」，由**宿主程序**执行，再把结果回灌给模型。它是一个**控制流协议**，不是数据格式。

关键差别在**谁执行**：JSON mode 的结果由你的代码消费；function calling 的结果由你的代码执行后、再交还给模型继续推理。

工程含义也不同：

- function calling 的 schema 会参与训练/对齐，模型对「什么时候该调用」有专门的倾向性；JSON mode 没有。
- function calling 天然支持多轮、并行、失败重试；JSON mode 只是单次输出。
- 如果你只是想抽字段，用 JSON mode 更省 token（不用带工具描述）。

## few-shot 示例该怎么挑？

三个原则，按重要性排序：

1. **覆盖边界，而不是覆盖常见**。模型本来就会的简单例子没有信息量；真正决定行为的是「模棱两可时怎么判」。所以示例要挑那些「人类也会犹豫」的样本。
2. **格式要完全一致**。示例里的字段顺序、缩进、是否带解释，模型都会模仿。示例格式不一致，输出就会漂移。
3. **数量和顺序都有影响**。3~5 条通常够用；超过 10 条收益递减还费 token。顺序上，模型对**最后一条**更敏感（近因效应），把最想让它模仿的放最后。

一个常见错误：示例全是正例。如果任务有「应该拒答」「应该输出空」的情况，必须给对应的示例，否则模型永远不拒答。

## 思维链为什么有效？什么时候反而有害？

有效的解释有两种：一是它把「一步到位的映射」拆成多个中间步骤，等效于给了模型更多计算量（更多 token 就是更多前向）；二是它让中间结果以自然语言落到上下文里，后续步骤可以「看见」前面的推理，减少遗忘。

有害的场景也很明确：

- **任务是纯检索/抽取**：思维链会引入无关推理，增加幻觉面。抽字段就该直接抽。
- **延迟敏感**：思维链让输出 token 数翻几倍，直接推高延迟和成本。
- **推理过程会被用户看到**：错误的中间步骤会削弱可信度，哪怕最终答案对。
- **模型本身弱**：小模型的思维链经常是「看起来像推理的胡说」，反而降低准确率。

工程建议：**先测再开**。同一个任务，开/关思维链各跑一遍评估集，看准确率和延迟的权衡。不要因为「听说思维链有用」就全局打开。

## 系统提示词该写多长？写长了会怎样？

不是越长越好，有三个真实的衰减机制：

1. **中间遗忘（lost in the middle）**：模型对上下文开头和结尾的内容记得最牢，中间段最容易被忽略。把关键约束放在开头或结尾。
2. **指令冲突**：写 50 条规则，必然有互相矛盾的（「回答要详细」vs「不超过三句」），模型会随机挑一条执行，表现成「时好时坏」。
3. **注意力稀释**：规则越多，每条分到的注意力越少，遵守率下降。

实践建议：

- 只写**能被验证**的规则。「要专业」无法验证，「每个结论必须带原文编号」可以验证。
- 规则数量控制在 10 条以内，超过就分层（系统提示词放硬约束，用户提示词放任务参数）。
- 每条规则配一个反例，比堆十条正向描述有效。
- 定期删规则：加了新规则后要回归测试，很多规则其实是历史包袱。

## 提示词里的「不要做什么」为什么经常失效？

因为语言模型的训练目标是「生成合理的续写」，而否定句在语义上仍然激活了被否定的概念。你说「不要提价格」，上下文里就出现了「价格」这个词，模型反而更容易提到它。

三个更可靠的替代写法：

1. **改成正向指令**：「只讨论产品的技术参数」比「不要讨论价格」好。
2. **给出替代行为**：「如果用户问价格，回答『请咨询销售』」——告诉它该做什么，而不是不该做什么。
3. **用结构约束代替语言约束**：字段白名单、枚举值、长度上限，让「不该出现的输出」在结构上无法生成。

同样的道理适用于「不要编造」：改成「每个结论必须附原文编号，没有依据的部分写『资料未提及』」，可验证、可检查。
