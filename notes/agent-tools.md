# 工具调用：怎么让模型用对工具

Agent 的能力上限，很大程度上由「工具设计」决定，而不是模型。工具描述写得含糊，再强的模型也会调错参数。这篇讲工具描述怎么写、失败怎么处理、什么时候该并行、工具太多怎么办。

## 工具描述怎么写，模型才用得对？

工具描述是**给模型看的文档**，不是给人看的注释。四条规则：

**1. 说清「什么时候用」，而不只是「是什么」。** 模型选错工具，多数是因为两个工具的用途描述有重叠。比如「搜索文档」和「搜索网页」，要明确写「当问题涉及内部资料时用前者，涉及实时信息时用后者」。

**2. 参数描述要带约束和示例。** 不要写 `date: string`，写 `date: 日期，格式 YYYY-MM-DD，例如 2026-10-28`。模型对格式的推断能力很差，但模仿示例的能力很强。

**3. 枚举值要穷举。** 如果参数只能是几个固定值，用 enum 列出来，别用自然语言描述「可以是几种类型」。

**4. 说明失败时的行为。** 比如「查不到返回空数组，不要编造」。模型在工具返回空时，很容易自己脑补内容。

一个反例：`search(query: string)`。这个描述等于没写——搜什么库？返回什么？多少条？模型只能猜。

一个正例：`search_docs(query: 检索关键词，用中文，2~5 个词；返回最多 5 条，每条含标题和摘要；没有结果时返回空数组)`。

## 工具调用失败了该怎么处理？

失败分三类，处理方式完全不同：

**1. 参数错误（可重试）**：模型给的参数格式不对（日期写成「明天」）。做法是**把错误信息回灌给模型**，让它自己修正——这是最有效的自愈方式，通常一次就能改对。

**2. 业务错误（可解释）**：工具执行了但业务上不成立（订单号不存在）。做法是把明确的业务语义回灌：「订单 A123 不存在，请确认单号」。不要只说「调用失败」，模型不知道该怎么调整。

**3. 系统错误（不可重试）**：超时、限流、服务挂了。做法是**重试有限次 + 降级**。重试要有退避，且要计入预算——否则一个挂掉的服务会把整个 agent 卡死。

三条工程约束：

- **必须有超时**。每个工具调用设独立超时（比如 10 秒），超时按失败处理，不能让 agent 无限等。
- **必须有重试上限**。同一个工具连续失败 2 次就放弃，换路径或直接告诉用户。
- **失败要可观测**。日志里记录「哪个工具、什么参数、什么错误」，否则线上排查只能靠猜。

一个容易忽略的点：**不要让模型看到原始异常堆栈**。它会被无关信息干扰，而且堆栈里可能含敏感路径。要在工具层把异常翻译成一句人类可读的原因。

## 什么时候该让模型并行调用工具？

当多个工具调用**互不依赖**时，并行能显著降低延迟。比如「查天气 + 查航班」，两者没有先后关系，串行是 2 倍延迟，并行是 1 倍。

判断标准很简单：**后一个调用的参数，是否依赖前一个的结果？**

- 依赖 → 必须串行（查用户 ID → 用 ID 查订单）。
- 不依赖 → 可以并行。

工程上的三种做法：

1. **模型自主并行**：支持 parallel tool calls 的模型会自己一次返回多个调用。适合工具多、关系简单的场景。
2. **编排层强制并行**：在代码里显式并行（`asyncio.gather`），适合流程固定的场景。可控性更好。
3. **不并行**：如果工具有副作用（写操作），并行会引入竞态，宁可串行。

一个坑：**并行调用的结果顺序不保证**。模型可能按调用顺序理解结果，所以编排层要显式标注「这个结果对应哪个调用」，别指望位置对应。

## 工具太多会怎样？怎么收敛？

工具数量超过 10~15 个后，会出现三个可观测的退化：

1. **选择准确率下降**：工具描述在上下文里互相干扰，模型容易选到「看起来相关但不是最优」的那个。
2. **上下文膨胀**：每个工具的描述都要占 token，20 个工具可能占掉 3000 token，挤压真正的任务信息。
3. **参数错误率上升**：工具越多，参数 schema 越容易混淆（多个工具都有 `id` 参数，但含义不同）。

四种收敛手段：

- **分层路由**：先用一个「选类别」的步骤缩小范围（查数据库 / 查文档 / 执行操作），再在类别内选具体工具。
- **工具合并**：把 5 个细粒度工具合成 1 个带 `action` 参数的工具。代价是参数变复杂，收益是选择变简单。
- **动态加载**：按当前任务只注入相关工具的描述（RAG 式的工具检索）。
- **子 agent**：把一组工具封给一个专职子 agent，主 agent 只看到一个「调用子 agent」的工具。

本项目的选择是「少而精」：agent 只有检索、改写、生成这几步，没有开放式的工具调用。原因是流程固定时，硬编码的编排比让模型自由选工具更可控——**不是所有 agent 都需要工具箱**。

## 工具调用的参数怎么校验？

**永远不要信任模型给的参数**，即使它看起来格式正确。

三层校验：

**1. Schema 层**：类型、必填、枚举、范围。JSON Schema 能覆盖大部分，但注意它校验不了语义（比如 `user_id` 是字符串但用户不存在）。

**2. 业务层**：参数的业务合法性。比如「日期不能是未来」「分页 size 不超过 50」「SQL 只能 SELECT」。

**3. 权限层**：**这一层最容易被跳过，也最危险**。模型不应该拥有比当前用户更大的权限。工具调用要以用户身份执行，而不是以「系统账号」执行。

为什么权限层关键：提示词注入可以让模型调用任意工具。如果工具用的是超级账号，一次注入就等于拿到了超级权限。正确做法是「工具内部用当前用户的 token 去查数据」，让数据库的权限体系兜底。

一个具体的反面案例：给 agent 一个 `run_sql(query)` 工具，用只读账号连库。看起来安全，但这个账号能读所有表——包括其他用户的数据。正确做法是「按当前用户过滤」写进 SQL，或者干脆不给通用 SQL 工具，只给「查我的订单」这种语义化工具。

**结论：工具设计的核心不是「让模型能做更多」，而是「让模型做不了不该做的事」。**
