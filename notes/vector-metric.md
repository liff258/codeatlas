# 距离度量与过滤检索：向量库最容易翻车的两处

距离度量的选择看起来是「随便选一个」，但它决定了以后能不能换索引；带过滤的向量检索看起来是「加个 WHERE」，实际是向量库最容易退化的地方。这篇讲清这两件事。

## 余弦相似度和内积有什么区别？

**余弦**只看方向：`cos(a,b) = a·b / (|a|·|b|)`，范围 [-1, 1]。它把「长度」归一化掉了。

**内积**同时看方向和长度：`a·b = |a||b|cosθ`，范围无界。

什么时候会有差别：当向量的**模长本身携带信息**时。比如推荐场景里，向量模长可能代表「热度」或「置信度」，这时候内积能利用这个信号，余弦会丢掉它。

在文本检索里，模长通常没有语义（它是模型输出的副产品），所以两者不该有差别——**前提是向量已经归一化**。

实际影响：

- 用余弦：不同长度的文档被公平对待，短文档不会被系统性压低。
- 用内积：如果向量没归一化，长文档（向量模长大）会占优势，这是一种隐性偏置。

结论：文本检索用余弦（或归一化后内积），别用未归一化的内积。

## 为什么归一化之后余弦和内积等价？

因为归一化把 `|a|` 和 `|b|` 都固定为 1，于是：

```
a·b = |a||b|cosθ = 1 × 1 × cosθ = cosθ
```

内积就等于余弦。同理，欧氏距离也有关系：

```
|a-b|² = |a|² + |b|² - 2a·b = 2 - 2cosθ
```

所以 L2 距离和余弦是单调对应的——距离最小等价于余弦最大。

工程意义：**归一化之后，三种度量的排序完全一致，可以自由切换索引类型而不重灌数据**。

这也是为什么很多向量库默认用内积（计算更快，省一次除法），但文档里建议「先归一化」。本项目就是入库前归一化 + 用余弦距离，注释里明确写了「以后换索引不用重灌」。

一个例外：**如果模型输出已经归一化**（部分模型会），再归一化一次也无害（幂等），所以不要省这一步——依赖「模型应该归一化了」是危险的假设。

## 带过滤条件的向量检索为什么容易翻车？

因为 HNSW 是「按距离顺序走图」，而过滤是「按属性筛掉一部分」。两者结合时，有两种执行策略，都有问题：

**策略一：先检索后过滤（post-filter）**。按向量距离取 top-k，再筛掉不满足条件的。

问题：如果过滤条件很严格（比如只占 1%），top-20 里可能一个都不满足，返回空结果。而且返回的结果数不可控——你要 20 条，可能只得到 1 条。

**策略二：先过滤后检索（pre-filter）**。先筛出满足条件的子集，再在这个子集里做向量检索。

问题：HNSW 的图结构是全局的，子集内的节点在图上可能不连通，搜索会走很多「死路」，延迟暴涨、召回暴跌。pgvector 在过滤条件选择性高时就会退化成顺序扫描。

**真实表现**：同一个查询，不加过滤是 0.5ms，加上 `WHERE subject = '并发'`（只占语料 16%）可能变成 40ms 甚至更慢——因为退化成了「全表扫描 + 排序」。

四种应对方案：

1. **分区索引**：按过滤维度（如学科）建独立的索引/集合。查询时直接路由到对应分区，过滤条件变成「选哪个索引」，不参与检索。
2. **部分索引（partial index）**：对高频过滤值建专用索引，比如 `WHERE subject='并发'` 的 HNSW。
3. **迭代扫描（iterative scan）**：pgvector 0.8+ 支持 `hnsw.iterative_scan`，允许在过滤时继续扩展搜索范围，缓解「结果不够」的问题。
4. **接受退化，加缓存**：如果过滤后的结果集很小且稳定，直接缓存结果。

选择建议：**过滤维度少且固定（学科、文档类型）→ 分区索引；过滤维度多且随机 → 接受退化，用两阶段（先粗筛 ID 再精排）**。

## 向量库和传统数据库该怎么配合？

三种架构，各有取舍：

**1. 一体化（向量能力内置在业务库里）**：比如 PostgreSQL + pgvector。

- 优点：**事务一致**（向量和业务数据在同一个事务里）、可以用 SQL 做复杂过滤和 JOIN、运维简单（不用多维护一个系统）。
- 缺点：超大规模（上亿向量）时性能不如专用库；索引类型选择少。
- 适用：数据量在千万级以内、需要强一致、团队不想多维护一套系统。**本项目就是这种**——5505 条向量放在业务库里，一条 SQL 就能 JOIN 出学科和文档名。

**2. 专用向量库（Milvus / Qdrant / Weaviate）**：向量和元数据都在向量库里。

- 优点：性能好、索引类型丰富、支持大规模。
- 缺点：**数据一致性要自己保证**——业务库更新了，向量库可能还是旧的；跨库 JOIN 要应用层拼。
- 适用：向量规模大、检索是核心负载。

**3. 混合（业务库 + 向量库双写）**：最常见的生产架构。

- 关键问题：**双写一致性**。删除文档时忘了删向量，就会检索到「幽灵结果」——向量还在，但原文已经没了，点开是 404。
- 应对：以业务库为准，向量库做异步同步 + 定期对账；或者给向量加「文档版本号」，检索后校验。

本项目的选择理由是「数据量小 + 要 JOIN + 要事务」：用 pgvector 一条 SQL 就能拿到「chunk 内容 + 学科 + 文档名」，如果拆成两个库，就要查两次再拼，还多了一个一致性风险。

## 召回率和延迟怎么权衡？ef_search 怎么调？

这是一个可以用数据回答的问题，不要凭感觉。

**测量方法**：固定一批标注好的 query（比如 50 条，每条标注正确答案的 ID），扫不同的 ef_search（20/40/80/160/320），记录两个数：Recall@20 和 P50/P99 延迟。画成曲线，找「拐点」。

典型曲线形状：ef 从 20 到 80，Recall 快速上升；80 到 320，Recall 只涨 1~2 个点，但延迟翻倍。**拐点通常在 Recall 达到 95% 的位置**。

调参的三个原则：

1. **按重要性分级**：普通查询用 ef=40，关键查询（用户手动点「深度检索」）用 ef=200。不必全局统一。
2. **P99 比 P50 重要**：HNSW 的长尾很明显，平均 5ms 但 P99 可能 50ms。要盯 P99。
3. **别只调索引**：如果 Recall 卡在 90%，加 ef 到 500 也只能到 92%，而加一路 BM25 召回可能直接到 96%。**先补路，再调参**。

本项目的实测可以作为参照：5505 条、1024 维、top_k=20，库内执行时间 0.35~0.56ms；扩到 55050 条后是 0.84~1.18ms——**10 倍数据只慢 2 倍**，因为 HNSW 是 log N 的。这说明在小规模场景下，向量检索根本不是瓶颈，优化精力应该放在切片、重排、提示词上。
