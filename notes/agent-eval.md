# Agent 评估与成本控制：怎么知道它真的在工作

Agent 比 RAG 更难评估，因为它的输出是一条「轨迹」而不是一段文本——中间调用了什么、为什么这么调，都会影响结果。这篇讲怎么评估轨迹、怎么防死循环、怎么控成本，以及最常见的失败模式。

## agent 怎么评估？只看最终答案够吗？

不够。最终答案只反映「这次成功了」，不反映「为什么成功」和「换个输入会不会崩」。

三个层次，缺一不可：

**1. 结果评估**：任务完成率、答案正确率。这是最基本的一层，但粒度太粗。

**2. 轨迹评估**：看中间步骤是否合理。

- **步数**：同样任务，别人 3 步完成，它用了 12 步，说明规划能力差或工具描述有问题。
- **工具选择准确率**：该用 A 工具时用了 B，即使最后答对，也是运气。
- **无效调用率**：重复调用同一个工具、用同样的参数调两次，都是浪费。
- **回退次数**：改写重查了几轮？回退多说明第一轮规划就错了。

**3. 鲁棒性评估**：换措辞、加噪声、给错误前提，看它会不会跟着错。比如问「AQS 的 CLH 队列为什么用双向链表」（前提就错了，CLH 是单向的），好的 agent 应该指出前提有误，而不是顺着编。

工程上的现实约束：轨迹评估需要人工标注或强模型裁判，成本高。所以常见做法是**用规则做粗筛**（步数、工具序列、是否超预算），人工只看异常样本。

## 怎么防止 agent 死循环？

四道闸，从软到硬：

**1. 最大步数（硬上限）**。最简单也最必要。没有这个，一个 bug 就能烧掉几百次调用。经验值：简单任务 5~8 步，复杂任务 15~20 步。

**2. 总超时（墙钟时间）**。步数没超但每步都慢，一样会卡死。设一个总预算（比如 60 秒），超了就降级输出当前最好的结果。

**3. 重复检测**。连续两次调用「同一个工具 + 相同参数」，直接判定为循环。注意要比较参数的**归一化形式**（排序 key、去空白），否则模型换个空格顺序就能绕过。

**4. 进展检测（最难但最有效）**。判断「这一步有没有让状态更接近目标」。实现方式可以是：记录每轮的关键状态（已获得哪些证据、已排除哪些假设），如果连续两轮状态没变化，就强制终止或换策略。

本项目的做法是前三道 + 一个改写次数上限：检索 → 自评 → 若不足则改写重查，**最多改写 2 轮**。第三轮开始收益极低（实测多数情况第一轮改写就能补齐），而成本是线性增长。

一个设计原则：**终止条件要在代码里，不要在提示词里**。「请不要重复调用」这种提示词约束，模型在压力下会忽略；而 `if steps > MAX: break` 是确定性的。

## agent 的成本怎么控制？

成本 = 调用次数 × 每次 token 数。两个乘数都要管。

**减少调用次数**：

- **砍掉不必要的模型调用**。这是收益最大的一项。本项目的 agent 原本每轮有 5 次模型调用（意图识别、规划、自评、改写、生成），实测发现其中 2 次可以不算：
  - 意图识别的输出只有 5 个枚举值 → 用关键词规则替代，判错代价接近零。
  - 自评（判断证据够不够）在证据充足时结论必然是通过 → 用重排分做阈值判断。
  - 结果：响应时间从 31 秒降到 13 秒，成本同步下降 40%。

- **缓存**：相同问题（归一化后）直接返回缓存结果。注意要在界面上标注「缓存」，否则用户会怀疑答案的真实性。

**减少单次 token**：

- **控制喂给生成的证据条数**。检索召回 12 条，但答案实际只引用前 6 条——后 6 条白占输入。减到 6 条后，输入 token 降 41%，生成时间从 11.6 秒降到 4.7 秒。
- **压缩历史对话**。多轮对话里，早期轮次只保留结论，不保留原文。
- **结构化输出**代替自然语言输出，减少冗余 token。

**分级策略**：简单问题走轻量路径（不规划、不重排），复杂问题走完整路径。判断依据可以是问题长度、是否含对比词、是否多跳。

## agent 常见的失败模式有哪些？

按出现频率排，前六种覆盖大多数问题：

**1. 工具选错**。描述重叠、工具太多。修描述比换模型有效。

**2. 参数幻觉**。编造不存在的 ID、日期、枚举值。解法：参数校验 + 错误回灌 + 枚举穷举。

**3. 死循环**。反复调用同一工具。解法：步数上限 + 重复检测。

**4. 过早收敛**。第一轮检索结果不好，就基于残缺证据编答案，不尝试改写。解法：显式的「证据够不够」判断 + 改写预算。

**5. 上下文污染**。中间某一步返回了错误信息，后续步骤全建立在错误前提上。解法：关键结论要求带出处；对高影响结论做二次校验。

**6. 任务漂移**。多轮之后忘了原始目标，被中间结果带偏。解法：每轮把原始目标重新注入（放在上下文末尾，利用近因效应）。

一个诊断技巧：**把 trace 打出来看**。多数 agent 的问题在 trace 里一目了然——你能看到它在第几步开始跑偏。本项目的做法是把每一步（节点名、耗时、状态、降级原因）都落库，前端可以回放。这比看最终答案有效得多。

## 多轮对话里，上下文该怎么管？

三条策略，按优先级：

**1. 只保留「结论 + 引用」，不保留原文**。上一轮检索到的 5 段原文，对下一轮通常没用；但「上一轮得出的结论」和「引用编号」有用。

**2. 显式摘要**。超过 N 轮后，把早期对话压成一段摘要（谁问了什么、得出了什么），替换原文。摘要要保留实体名和数字，这两类信息最容易在压缩中丢失。

**3. 检索式记忆**。不在上下文里堆历史，而是把历史存起来，需要时按当前问题检索相关片段。适合长会话（几十轮），代价是多一次检索。

一个具体的预算模板（按 8k 上下文算）：

- 系统提示词：500 token
- 历史摘要：300 token
- 最近 3 轮完整对话：1500 token
- 本轮检索证据：2000 token
- 输出预留：1500 token
- 余量：2000 token（给工具描述、意外情况）

关键原则：**给输出留足空间**。很多人把上下文塞满，结果模型生成到一半被截断，答案不完整——这比少给点证据糟糕得多。
