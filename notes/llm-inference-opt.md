# 推理优化：量化、投机解码与采样参数

「模型太慢太贵」是落地时绕不过去的问题。这篇讲四种优化（量化、投机解码、PagedAttention、批处理）的原理与边界，最后解释采样参数，以及为什么同一个问题两次回答不一样。

## 量化为什么能提速？INT8 和 INT4 差在哪？

量化是把权重（和激活）从 fp16/bf16 压到更低位宽。它提速有两个机制，别混为一谈：

1. **显存带宽**：decode 阶段是 memory-bound，每步要把权重从显存读一遍。fp16 → int8，要读的数据少一半，速度理论上接近翻倍。这是主要收益来源。
2. **算力**：低位宽整数运算的吞吐更高，但只有在 compute-bound 的 prefill 阶段才明显。

INT8 和 INT4 的差别：

- **INT8**（如 LLM.int8()）：精度损失很小，通常 <0.5% 的指标下降。难点在激活值的离群通道——少数通道的数值比其他大几十倍，直接量化会把它们压平。LLM.int8() 的做法是把这些离群维度抽出来用 fp16 算，其余用 int8，混合精度。
- **INT4**（如 GPTQ、AWQ）：显存再减半，7B 模型权重只需 3.5GB，消费级显卡能跑。代价是精度损失开始可见，且对校准数据敏感——校准集选得不对，某些能力会明显退化。

实践判断：显存够、只求稳 → INT8；显存紧、要本地部署 → INT4 + 挑好校准集，并且一定要在自己的任务上验一遍，别只看困惑度。

## 投机解码是怎么加速的？为什么说它是无损的？

思路是「用小模型猜，用大模型验」：

1. 一个小的 draft 模型先连续生成 k 个 token（很便宜）。
2. 大模型把这 k 个 token 一次性并行验证（一次前向，等价于处理 k 长度的序列）。
3. 从头开始比对，接受前缀直到第一个不一致的位置，然后由大模型自己出那一个 token。

关键点：**验证是一次并行前向，成本约等于生成 1 个 token**。所以只要平均接受长度 >1，就有净收益。

无损性来自接受准则：不是「一样就接受」，而是按概率比 min(1, p_large/p_draft) 接受，被拒绝的位置从修正后的分布重新采样。数学上保证最终输出的分布和大模型单独采样完全一致。

收益取决于**接受率**，而接受率取决于 draft 模型和大模型的分布有多接近。同系列的小模型（如 1B 配 70B）接受率高；跨家族基本没用。典型加速 1.5~2.5 倍，代码补全这类「确定性高」的任务收益最大。

## PagedAttention 解决了什么问题？

它解决的是 KV Cache 的**显存碎片**。

原来的做法是按请求的最大长度（max_len）预分配一块连续显存。但实际生成长度不可预测，平均只用 20%~40%，剩下的全浪费——浪费的显存本来可以用来跑更多并发。

PagedAttention 借了操作系统虚拟内存的思路：

- KV Cache 切成固定大小的 block（比如 16 个 token 一块）。
- 每个请求维护一张 block 表，逻辑上连续、物理上可以不连续。
- 按需分配，用完即回收；不同请求还能共享同一个 block（比如相同的系统提示词）。

效果：显存浪费从 60%~80% 降到 4% 以内，同等显存下并发数提升 2~4 倍，吞吐随之上去。这是 vLLM 的核心创新，现在基本是推理框架的标配。

## temperature、top-k、top-p 分别在改什么？

三者都在改「下一个 token 从哪个分布里采样」，但作用点不同：

- **temperature**：先把 logits 除以 T。T<1 让分布更尖（更确定），T>1 让分布更平（更随机），T=0 退化成贪心。它改的是分布的**形状**。
- **top-k**：只保留概率最高的 k 个候选，其余置零。它改的是候选集的**大小**，是固定的。
- **top-p（nucleus sampling）**：按概率从高到低累加，直到累计概率达到 p，只在这个集合里采样。候选集大小随分布自适应——模型很确定时候选集很小，不确定时自动变大。

实践配置：要确定性输出（结构化抽取、代码生成）用 T=0 或 0.1；要创意（文案、头脑风暴）用 T=0.8~1.0 配 top-p=0.95。**不要同时用 top-k 和 top-p 的激进值**，会把分布削得太窄，输出变得重复。

## 为什么同一个问题两次回答不一样？temperature=0 也会吗？

两个层面：

**采样随机性**：T>0 时按概率采样，两次自然不同。这是设计如此。

**浮点非确定性**：即使 T=0（贪心），输出也可能不同。原因：

1. **batch 组成变化**：GPU 上的矩阵乘会把多个请求拼成一个 batch，不同 batch 形状下，归约（reduction）的分块方式和累加顺序不同，浮点误差就不同。某个 token 的 logits 差 1e-4，在两个候选几乎并列时就会翻转。
2. **kernel 的非确定性实现**：某些算子（如原子加、并行归约）本身不保证顺序一致。
3. **专家并行/MoE 路由**：路由在边界情况下可能选中不同专家。

工程含义：**不要把「复现同一个答案」当成系统保证**。需要可复现时，固定 batch 大小、关掉连续批处理（continuous batching）、用确定性 kernel，代价是吞吐大幅下降。对 RAG/Agent 这类系统，正确的做法是接受不确定性，用「断言关键事实」而不是「比对全文」来写测试。
