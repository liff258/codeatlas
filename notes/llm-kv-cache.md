# LLM 推理：两个阶段与 KV Cache

大模型推理慢，慢在哪里、显存被什么吃掉了，是面试里区分「用过 API」和「真的部署过」的第一道题。这篇把 KV Cache、MQA/GQA、prefill/decode、显存估算这几件事串起来讲，最后给出可以背下来的估算公式。

## 什么是 KV Cache？为什么它能把推理加速几倍？

自回归生成是逐 token 的：每生成一个 token，都要对「前面所有 token」做一次注意力。如果不做任何缓存，第 t 步就要重新计算前 t 个 token 的 K（键）和 V（值），总计算量是 1+2+…+n，也就是 O(n²)。

KV Cache 的做法很直接：每层算出来的 K、V 存起来，下一步只算新来这个 token 的 K/V，然后和缓存拼接。于是每步的注意力计算从「对 n 个 token 全算一遍」变成「对 1 个 query 和 n 个 key 做点积」，生成 n 个 token 的总计算量从 O(n²) 降到 O(n)（严格说是每步 O(n)，总计 O(n²) 里的常数项大幅下降）。

实测收益：7B 模型、2k 上下文，开 KV Cache 后吞吐通常提升 3~10 倍，上下文越长差距越大。代价是显存——用空间换时间，而这个空间并不小。

## KV Cache 的显存到底占多少？怎么估？

公式：`2 × 层数 × 隐藏维度 × 序列长度 × batch × 每元素字节数`。前面的 2 是 K 和 V 各一份。

以 7B 模型为例（32 层、hidden 4096、fp16 即 2 字节）：单 token 的 KV Cache = 2 × 32 × 4096 × 2 = 524288 字节，约 0.5MB。听起来不多，但 8k 上下文就是 4GB，32 并发就是 128GB——比模型权重（7B × 2 字节 = 14GB）大得多。

所以部署时的显存分配大致是：权重 + KV Cache + 激活值 + 框架开销。长上下文场景下，KV Cache 往往是大头，这也是为什么「支持 128k 上下文」的模型，实际并发数会掉得很厉害。

## MQA 和 GQA 为什么能省显存？代价是什么？

标准多头注意力（MHA）里，每个头都有独立的 K/V，所以 KV Cache 随头数线性增长。

MQA（Multi-Query Attention）让所有头共享同一份 K/V：KV Cache 直接降到 1/头数。32 头的模型就是 1/32，显存压力骤降，decode 阶段要读的数据也少了，所以更快。

代价是表达能力下降——所有头看同一组键值，注意力的多样性被压缩，训练时也更不稳定，小模型上掉点明显。

GQA（Grouped-Query Attention）是折中：把头分组，每组共享一份 K/V。比如 32 个头分 8 组，KV Cache 降到 1/4，质量接近 MHA。Llama 2 70B、Llama 3 全系、Qwen 系列都用 GQA，它基本是当前的主流选择。

一句话记：MQA 省得最狠但掉点，GQA 是「省 4 倍、几乎不掉点」的工程解。

## prefill 和 decode 两个阶段的瓶颈有什么区别？

推理分两段：

**prefill（预填充）**：把整段 prompt 一次性送进模型，所有 token 并行计算。这一步是 compute-bound（算力受限），GPU 利用率高，吞吐大。用户感知到的是「首 token 延迟（TTFT）」，和 prompt 长度近似线性相关。

**decode（解码）**：逐 token 生成，每步只算一个 token，但要把整个 KV Cache 和全部权重从显存读一遍。这一步是 memory-bandwidth-bound（显存带宽受限），算力大量闲置。用户感知到的是「每秒吐多少字（tok/s）」。

这个区分很实用：TTFT 高 → 优化 prompt 长度、加 prefix caching；吐字慢 → 优化 batch、量化权重、换更快的卡。两者要调的东西完全不同。

## 上下文窗口变长，为什么推理是平方级变慢？

三个原因叠加，都指向 n²：

1. **注意力本身是 O(n²)**：每个 token 要和前面所有 token 算相关性。
2. **KV Cache 显存是 O(n)**：每步都要把这份缓存读一遍，decode 总时间是 O(n²)。
3. **prefill 阶段是 O(n²) 的矩阵乘**：长 prompt 的 TTFT 会明显变长。

工程上还有第四层：注意力之外的 FFN 部分是 O(n)，但显存带宽和调度开销会放大常数项。

所以「上下文翻倍，成本翻四倍」不是厂商在收费上做文章，是注意力的数学性质。这也是长上下文模型要搞滑窗注意力、稀疏注意力、线性注意力的原因。

## 除了 PagedAttention，还有哪些省显存的办法？

- **PagedAttention**：把 KV Cache 按固定大小的 block 管理（借鉴操作系统虚拟内存），消除预分配造成的碎片。原来按 max_len 预留，实际用不到一半，浪费 60%~80%；分页后按需分配，vLLM 靠这个把吞吐提了 2~4 倍。
- **Prefix Caching**：系统提示词、few-shot 示例这些前缀每次都一样，把它们的 KV 缓存下来复用，TTFT 能降一个数量级。
- **KV Cache 量化**：fp16 降到 int8，显存直接减半，精度损失通常可接受（K 比 V 更敏感）。
- **滑窗 / 稀疏注意力**：只保留最近 n 个 token 的完整 KV，更早的丢弃或压缩（StreamingLLM 保留开头的 attention sink）。
- **GQA/MQA**：从结构上减少 KV 头数，见上文。

这些手段不互斥，生产环境通常是「GQA + PagedAttention + Prefix Caching + int8 KV」一起上。
