# RAG 失败归因：答错了，是哪一步错的

RAG 出问题时的第一反应通常是「换个更好的模型」。但多数错误不在生成，在检索——模型只是忠实地把错误证据组织成了通顺的答案。这篇讲怎么把错误归因到具体环节，以及为什么不能只看最终答案。

## RAG 答得不好，怎么判断是检索的问题还是生成的问题？

一个动作就能区分：**把正确答案的原文直接塞给模型，再问一次。**

- 塞了原文还答错 → **生成问题**（提示词、模型能力、上下文组织）。
- 塞了原文就答对 → **检索问题**（召回没覆盖到、排序没排上来、切片切碎了）。

这个「人工 oracle 实验」成本极低但极其有效，应该作为排查的第一步，而不是最后一步。

确定是检索问题后，再往下切一层：

1. **库里有没有？** 直接查数据库全文搜索关键词。没有就是素材缺口，调什么参数都没用。
2. **召回了没？** 看 top-50 里有没有正确答案。有但没进 top-10 → 排序问题（上重排）；top-50 都没有 → 召回问题（换 embedding、加关键词路）。
3. **召回了但被切碎？** 看命中的片段是否完整包含答案。切碎了就是切片问题，要往上聚合。

本项目就踩过第 3 种：标准答案的 chunk 被召回，但只包含答案的前半段，生成的答案因此缺了一半。看起来像「模型不会总结」，实际是切片问题。

## 忠实度（faithfulness）怎么衡量？

忠实度 = 答案里的每个结论，是否都能在提供的证据里找到依据。它和「答案对不对」是两件事——一个完全忠于错误证据的答案，忠实度满分但事实错误。

三种衡量方式：

**1. 引用检查（最硬）**：要求模型给每个结论标引用编号，然后程序检查：编号是否越界、被引用的片段是否真的包含该结论。前一半可以完全自动化，后一半需要模型或人工判断。

关键设计：**编号由代码分配，不由模型生成**。把候选证据编号后写进提示词，模型只能引用已存在的编号；越界的编号保留正文但标记「无出处」。这样「引用」就从装饰变成了可验证的约束。

**2. 句子级归因（NLI 式）**：把答案拆成句子，逐句判断「这句是否被证据支持」（蕴含/中立/矛盾）。可以用小模型做，成本可控。

**3. LLM 裁判**：让另一个模型判断「答案是否只使用了给定证据」。方便但有偏差（倾向于说「是」），需要抽检校准。

工程上推荐 1 + 2 组合：引用检查抓「无出处」，句子级归因抓「有出处但曲解」。

## 为什么不能只评估最终答案？

因为最终答案是一个**复合指标**，它把三种能力的表现混在一起：检索质量、生成质量、以及「模型是否诚实地承认不知道」。只看它，无法定位问题，也无法判断改进是否有效。

分层评估的最小集合：

| 层 | 指标 | 怎么测 |
|---|---|---|
| 检索 | Recall@k / Hit@1 | 标注「答案在哪个 chunk」，看有没有被召回 |
| 排序 | MRR / nDCG | 看正确答案排在第几 |
| 生成 | 忠实度、要点覆盖率 | 引用检查 + 句子归因 |
| 拒答 | 该拒答时是否拒答 | 专门构造「库里没有」的问题 |

最后一行最容易被忽略。一个只会答题、不会说「不知道」的系统，在演示时很漂亮，在真实使用中很危险——用户无法区分「它说没有」和「它没找到」。

本项目的做法是：证据覆盖率低于阈值时，先改写重查（最多 2 轮），仍不足则要求答案开头写明「现有资料不足以完整回答」。这是提示词约束，不是硬门控，所以评估里要专门测「它有没有真的这么说」。

## 怎么做 RAG 的回归测试？

RAG 的组件太多（切片、embedding、索引、检索参数、重排、提示词、模型），任何一处改动都可能悄悄影响效果。回归测试要解决的是「改 A 有没有弄坏 B」。

四层测试，从便宜到贵：

**1. 单元测试（秒级，每次提交跑）**：RRF 融合的排序正确性、切片不跨标题、引用编号不越界、JSON 容错解析。这些是纯函数，不需要模型和数据库。

**2. 检索回归（分钟级，改检索参数时跑）**：固定评估集，跑 Recall@k / Hit@1，和基线对比。**掉超过阈值就回滚**。本项目的阈值是 Hit@1 掉 2 个点。

**3. 生成回归（十分钟级，改提示词时跑）**：同一批证据，看输出是否仍满足约束（格式、引用、长度）。这层不用人看，写断言即可。

**4. 端到端抽检（人工，发版前）**：抽 5~10 条真实问题，人读一遍。机器指标看不出「答案读起来很别扭」这类问题。

一个实践细节：**基线要存在仓库里**。每次跑完把指标写进文件，和上次对比。没有基线，就只能说「感觉快了/准了」，说不出具体数字——而这在答辩或复盘时是最没有说服力的。

## 幻觉能被彻底消除吗？

不能。原因在机制层面：模型是一个概率生成器，它的目标函数是「生成合理的下一个 token」，不是「生成真实的话」。在没有证据的情况下，它也会生成看起来合理的内容——这不是 bug，是它的工作方式。

能做的只有四件事，按有效性排序：

1. **减少「无证据生成」的机会**：检索到位、证据明确、要求引用。模型在有据可依时，幻觉率会大幅下降。
2. **让幻觉可检测**：强制引用 + 越界标记 + 出处可点开。用户能自己验证，比任何「准确率 99%」的宣称都可信。
3. **让不知道可表达**：给模型一个「资料不足」的出口。没有出口时，它只能编。
4. **降低幻觉的后果**：敏感场景加人工确认，不让模型直接执行不可逆操作。

一个诚实的说法：**RAG 不消除幻觉，它把「凭空编造」变成「有据可查的引用 + 可被发现的偏差」。** 这是工程上能做到的最好状态，也是应该对用户明确说明的边界。
