# Embedding 模型：选型、归一化与维度

embedding 是 RAG 的地基，但它不是「越贵越好」。这篇讲模型怎么选、为什么必须归一化、维度是不是越高越好、中文场景的坑，以及什么时候值得微调 embedding。

## embedding 模型怎么选？

四个维度评估，按重要性排序：

**1. 语言覆盖**。中文场景必须选多语言或中文优化的模型。用纯英文模型（如早期 all-MiniLM）处理中文，效果会掉一大截——这不是调参能救的。bge-m3、text-embedding-3、Qwen-Embedding 这类多语言模型是常见选择。

**2. 最大输入长度**。多数模型是 512 token，bge-m3 支持 8192。如果你的切片是 800 字，用 512 窗口的模型会被截断——**截断是静默的**，不报错，只是向量只覆盖了前半段。

**3. 检索任务上的表现**。看 MTEB/C-MTEB 榜单，但要注意：榜单是通用任务的平均分，你的领域（比如代码、法律、医疗）表现可能完全不同。**必须用自己的评估集验一遍**。

**4. 部署成本**。API 调用（按 token 计费、有网络延迟）vs 本地部署（要 GPU/CPU、要加载时间）。本项目的 bge-m3 是本地 CPU 推理，5505 条切片编码约 16 分钟，查询编码 85ms——这个延迟在演示环境可接受，但高并发场景就得换方案。

一个常被忽略的点：**换 embedding 模型必须重建整个索引**。不同模型的向量空间不兼容，混用会得到完全错误的结果。所以选型要一次定好，别指望「先用便宜的，以后换好的」。

## 向量一定要归一化吗？

取决于你用哪种距离度量，但**归一化几乎总是对的**。

三种度量的关系：

- **余弦相似度**：只看方向，不看长度。范围 [-1, 1]。
- **内积**：方向和长度都算。范围无界。
- **欧氏距离（L2）**：看绝对位置差。

关键恒等式：**向量归一化之后，余弦相似度、内积、欧氏距离的排序完全一致**。因为归一化把长度固定为 1，三者只差一个单调变换。

所以工程上的最佳实践是：**存进去之前先 L2 归一化，然后用内积或余弦检索**。好处是以后换索引类型（余弦 → 内积 → L2）不用重新灌库，排序结果不变。

本项目的做法就是这样：入库前归一化，查询时也归一化，距离用余弦（`<=>`）。注释里写明了「以后换索引不用重灌」。

一个陷阱：**有些模型的输出不是单位向量**，但也没人告诉你。所以不要假设，显式归一化一次。

## 维度越高越好吗？

不是。三个约束：

**1. 存储与带宽线性增长**。1024 维 float32 = 4KB/条。100 万条就是 4GB，加上 HNSW 图结构要 6~8GB。

**2. 检索延迟随之上升**。每次距离计算是 O(d)，高维下常数项明显。1024 维比 384 维慢约 2.5 倍。

**3. 高维的「距离集中」现象**。维度越高，随机向量之间的余弦相似度越集中在 0 附近，区分度反而下降——这就是维度灾难的一种表现。所以「更多维度」不必然带来「更好区分」。

实践上：

- 通用语义检索，384~1024 维足够。
- 需要细粒度区分（比如区分相似但不同的 API）时，高维有帮助。
- 有些模型支持 **Matryoshka 表示**（嵌套维度）：一个 1024 维向量，前 256 维就能当低维版本用，可以先粗筛再精算，省成本。

判断方法还是评估集：同一个模型的不同维度（如果支持截断），跑一遍 Recall@k，看 512 维和 1024 维差多少。差 1 个点以内，就该用 512。

## 中文场景为什么要用多语言模型？

三个具体原因：

**1. 分词与语义粒度**。中文没有空格，英文模型的分词器会把中文切成字节级碎片，语义信息在第一步就损失了。

**2. 中英混排**。技术文档里「线程池 ThreadPoolExecutor」这种混排极常见，模型要能理解「线程池」和「ThreadPoolExecutor」是同一个东西。

**3. 跨语言检索**。问中文问题、检索英文论文，是 AI 领域的常态。多语言模型能把两者映射到同一空间，单语言模型做不到。

本项目的教训很具体：AI 域素材早期以英文论文为主，中文提问检索英文内容时，**BM25 完全失效（字面不匹配），只能靠向量**。补了中文笔记之后，BM25 立刻恢复竞争力（AI 域 Hit@1 从 46.2% 提到 58.8%）。

结论：**跨语言检索是 embedding 的责任，不是 BM25 的**。这也说明为什么 AI 域必须用多语言模型。

## embedding 模型能不能微调？什么时候值得？

能，但**大多数场景不值得**。

什么时候值得：

1. **领域词汇特殊**：医疗、法律、代码，通用模型分不清「心肌梗死」和「心梗」的等价性。
2. **有大量标注对**：至少几千条「query → 正确文档」的配对，否则微调只会过拟合。
3. **通用模型已经调到极限**：检索 Recall 卡在某个值上，其他手段都用过了。

什么时候不值得：

- 数据量小（几百条）—— 不如直接用更好的基座模型。
- 问题是「库里有但没召回」—— 先查是不是切片或索引问题。
- 只是想让「某些词更相关」—— 用 BM25 混合检索更便宜。

微调的技术路线（对比学习）：用 (query, positive, negative) 三元组，优化 InfoNCE 损失。难点在**负样本挖掘**——随机负样本太简单（模型早就会区分），要用「当前模型认为相关但实际不相关」的 hard negative，才有提升。

一个现实建议：**先把混合检索和重排做好，再考虑微调 embedding**。前者是几行代码，后者是几周工程。

## 同一个模型，query 和 document 要区别对待吗？

要。很多模型是**非对称**的，训练时 query 和 document 用了不同的前缀或不同的编码方式。

两种常见形式：

1. **指令前缀**：bge 系列要求在 query 前加「为这个句子生成表示以用于检索相关文章：」，document 不加。漏掉前缀会让效果下降几个点。
2. **独立编码器**：某些模型 query 和 doc 走不同塔（虽然现在少见）。

工程上要做的是：**把「编码 query」和「编码 document」做成两个不同的函数**，而不是一个通用 `encode()`。本项目就是这样做的——`encode(texts, is_query=True/False)`，避免调用方忘记加前缀。

另一个细节：**批量编码时不要把 query 和 doc 混在一个 batch 里**。有些模型的 batch 内归一化会互相影响（虽然少见），更重要的是混在一起容易漏掉前缀处理。
