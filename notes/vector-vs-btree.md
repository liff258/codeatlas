# 向量检索为什么不能用 B+ 树加速

> 本文为 CodeAtlas 项目自写素材，用于打通「后端」与「AI」两个知识域之间的概念连接。
> 许可证：项目原创，随仓库分发。

## 为什么这个问题值得单独写

在面试和工程实践里，「B+ 树」和「向量检索」通常出现在两个完全不同的语境里：
前者是 MySQL 索引、磁盘 I/O、范围查询；后者是 embedding、余弦相似度、ANN 近似搜索。

于是很多人会产生一个自然的联想：既然 B+ 树能把一维数据的查找从 O(n) 降到 O(log n)，
那高维向量是不是也能用同样的结构加速？

这个联想是错的，但错得很有价值——因为它逼着你去想清楚一件事：
**B+ 树到底在利用数据的什么性质？当这个性质不存在时，它还能不能成立？**

本文就是把这个「为什么不行」拆开讲清楚，然后说明真正可行的方案在利用什么。

## 先看 B+ 树：它优化的到底是什么

B+ 树的本质是一棵**多路平衡搜索树**，它的所有设计都服务于同一个目标：
**减少磁盘 I/O 次数**。

几个关键设计：

- **高扇出**。一个节点存放几百个 key，树高通常只有 3~4 层。
  这意味着查一条记录最多 3~4 次磁盘读取，而不是几十次。
- **数据只在叶子节点**，内部节点只存索引 key。这让内部节点能塞下更多 key，进一步压低树高。
- **叶子节点用双向链表串起来**。这是范围查询 `WHERE id BETWEEN 100 AND 200` 能做到
  「定位起点 + 顺序扫描」的原因，不需要回到根节点重新找。

但请注意最核心的那一条，它藏在「搜索树」三个字里：

> **B+ 树要求数据之间存在一个全序关系（total order），并且这个顺序要能指导查找方向。**

给你一个 key，B+ 树能告诉你「往左走还是往右走」，是因为 key 之间可以比较大小，
而且这个大小关系和数据在磁盘上的物理排列是一致的。

对于整数、字符串、时间戳，这个前提天然成立。

## 再看向量检索：它要解决的是什么问题

向量检索的输入是一个查询向量 q（比如 1024 维），和库里几百万个文档向量。
目标是找出**距离 q 最近的 K 个向量**。

关键区别在这里：

- B+ 树问的是「这个 key 等于多少 / 在哪个区间」——**精确匹配与范围**。
- 向量检索问的是「哪个向量离 q 最近」——**相似度排序**。

而且这个「最近」是在**高维空间**里定义的。余弦相似度、内积、欧氏距离，
它们衡量的是方向或位置的整体接近程度，不是某一个维度的数值大小。

## 核心矛盾：高维空间里没有「有用的」全序

有人会想：那我把向量按某种规则排序不就行了？比如按第一个维度排？

问题在于：**按任一维度排序，都会破坏其他维度上的邻近关系。**

两个向量在第 1 维上差得很远，但它们可能在其余 1023 维上几乎一样，
整体余弦相似度高达 0.98。如果按第 1 维排序，这两个向量会被排到数组两端，
检索时永远不会被放在一起考虑。

那有没有一种排序，能同时尊重所有维度？

数学上确实有——**空间填充曲线**（Z-order 曲线、Hilbert 曲线）就是干这个的：
它把高维空间里的点映射到一维线上，并尽量保持「空间上近的点在线上也近」。

但在高维下，这个「尽量」会迅速失效：

- 二维、三维时，Hilbert 曲线的局部性保持得很好。
- 到了 100 维以上，曲线会频繁地「跳跃」，空间上相邻的点在曲线上可能隔了很远。
  这种现象叫**局部性丧失**（locality loss）。

结果就是：用空间填充曲线给向量排序后建 B+ 树，查询时得扫描大量不连续的区间，
退化成接近全表扫描。

## 维度灾难：为什么高维让一切「基于划分」的方法失效

「维度灾难」（curse of dimensionality）这个词被用得很泛，但对检索来说，
最致命的是这一条：

> **在高维空间里，任意两个随机点之间的距离会趋于相等。**

直观解释：假设每个维度独立同分布，那么两点距离的平方是各维度差值的平方和。
维度越高，这个和越接近它的期望值，相对波动越小。
也就是说，**「最近邻」和「第十近邻」的距离差会越来越小**，
「谁更近」这个判断本身变得越来越没有区分度。

这对所有「用超平面把空间切开、然后只搜其中一块」的算法都是灾难：

- **KD 树**：每次用一个维度把空间切成两半。低维（≤ 20 维左右）效果很好，
  但高维下几乎所有点都落在切分面附近，剪枝条件失效，退化成暴力搜索。
- **R 树 / R* 树**：用最小外接矩形包住点集。高维下这些矩形会大面积重叠，
  查询时不得不访问几乎所有分支。
- **B+ 树**：本质是一维的划分，连「切分高维空间」都做不到。

这就回答了标题的问题：

> **B+ 树不是「不够快」，而是它的前提在高维向量上根本不成立。**
> 它需要一个能指导查找方向的全序，而高维空间里不存在这样的全序。

## 一个常见的反驳：那为什么不用 B+ 树存「降维后的值」

这个想法是：先用 PCA 把 1024 维降到 1 维，再用 B+ 树索引这一维。

问题有两层：

1. **降维会丢失信息**。PCA 保留的是方差最大的方向，但方差大不等于「对区分最近邻有用」。
   两个向量在主成分上很接近，在次要成分上可能差别很大，降维后就被误判为相似。
2. **即使降维成功，也只能当粗筛**。工业界的做法确实有「先粗筛再精排」，
   但粗筛用的是专门为高维设计的结构（如 IVF 的聚类中心），不是 B+ 树。
   而且粗筛之后必须回到原始维度做精确距离计算，否则召回率会崩。

换句话说，B+ 树在这里最多能当个「桶定位器」，而桶内仍然要暴力算距离。
既然桶内要暴力算，那还不如直接用为高维设计的索引。

## 真正可行的方案在利用什么

理解了「B+ 树为什么不行」，就能理解为什么这些方案可行——它们都在**放弃精确性**，
换取**可接受的召回率 + 可控的延迟**。这个 trade-off 叫 ANN（Approximate Nearest Neighbor）。

### HNSW：用图代替树

HNSW（Hierarchical Navigable Small World）是目前工业界最主流的方案，也是本文档库
另一篇素材（原始论文）的主题。

它的核心思想：

- 把每个向量当作图上的一个节点，近邻之间连边。
- 建多层结构：上层稀疏（用于快速跳跃）、下层稠密（用于精确定位）。
  查询时从最上层的一个入口点开始，贪心地向「离 q 更近的邻居」移动，
  走到局部最优后下沉一层，重复这个过程。
- 这个结构和**跳表**（skip list）在思想上高度相似——都是用多层索引把
  O(n) 的线性扫描降到 O(log n) 级别的跳转次数。

注意这里的关键差别：HNSW 的「层」不是按 key 的大小划分的，
而是按**图的连通性**组织的。它不需要全序，只需要「谁离谁近」这个局部信息。

### IVF：先聚类，再只在最近的几个簇里搜

IVF（Inverted File）用 k-means 把向量聚成几千个簇，查询时先算 q 到各簇中心的距离，
只在最近的 nprobe 个簇里做暴力搜索。

它放弃了「全局最优」，换来了「只搜一小部分数据」。

### PQ：把向量压缩，用精度换内存

PQ（Product Quantization）把 1024 维切成若干段，每段用一个码本里的编号代替，
把 float32 的向量压成几个字节。距离计算改用查表，速度提升一个数量级，代价是精度损失。

工业系统通常把三者组合：**IVF 粗筛 + PQ 压缩 + HNSW 图索引**，
在不同场景下调参数平衡召回率与延迟。

## 回到 RAG：召回率该怎么提

上面讲的是「向量检索怎么做得快」。但对 RAG 系统来说，真正的痛点往往不是快，
而是**召回得准不准**。结合本项目实测（5219 个 chunk 的知识库），有几条经验：

### 1. 混合检索：别指望向量解决一切

在本项目的评测里，出现了一个反直觉的结果：

- 问「G1 收集器的 SATB 是什么」这类**含罕见术语**的问题，BM25（关键词）的
  top-1 命中率是 60%，而纯向量只有 33%。
- 但问「多个线程同时改一个数怎么保证不出错」这类**口语化**问题，
  向量能召回 CAS 乐观锁，BM25 却只召回了读写锁（词面相近但不对）。

原因是：向量把「SATB」和「G1 收集器」编码到了相近的位置，语义上没错，
但丢失了「SATB」这个精确标识；而 BM25 恰好相反，它只认字面，不理解语义。

两者互补，所以用 RRF（Reciprocal Rank Fusion）把两路结果按排名融合，
总体 Recall@5 从单路的 80% / 75% 提升到 90%。

### 2. 重排（rerank）：召回之后的第二道关

混合检索能保证「正确答案在候选里」，但排不到第一位。这时候需要 cross-encoder
（如 bge-reranker）对「查询-文档」对逐条打分。它比向量检索慢得多，
但只看前 20 条，成本可控。

本项目实测：RRF 融合后 Hit@1 只有 46.7%，还不如纯 BM25 的 60%——
这个差距**调 RRF 的参数修不了**（k 从 1 扫到 60 都试过），
必须靠 reranker 解决。

### 3. 切片策略：父子块比调模型更划算

检索要短（256 token 的块向量更聚焦），生成要全（1024 token 才有上下文）。
用 child 检索、命中后取它的 parent 喂给模型，召回率和答案质量能同时提升，
代价只是存储翻倍。

这个改动比换 embedding 模型便宜得多，收益却更直接。

### 4. 查询改写：让问题更像文档

用户问「向量检索为什么慢」，文档里写的是「近似最近邻搜索的复杂度分析」。
中间这条语义鸿沟，靠 embedding 是补不上的——因为问题本身就缺关键词。

可行的做法是先用 LLM 把问题改写成几个不同角度的子查询，分别检索再合并。
这也是本项目 Agent 里「自评-改写」这一步的动机：先判断证据够不够，不够就改写重查。

## 一张对照表

| 维度 | B+ 树 | HNSW / IVF / PQ |
|---|---|---|
| 数据形态 | 一维可比较的 key | 高维向量 |
| 依赖的性质 | 全序关系 | 局部邻近关系 |
| 查询语义 | 精确匹配、范围扫描 | 相似度 Top-K |
| 是否精确 | 精确 | 近似（用召回率换延迟） |
| 主要成本 | 磁盘 I/O | 内存 + 计算 |
| 典型场景 | 数据库索引、文件系统 | 向量库、语义检索 |
| 能不能互换 | 不能。前提不成立，不是性能问题 | 不能。B+ 树无法表达高维邻近 |

## 一句话总结

B+ 树之所以不能加速向量检索，不是因为它慢，而是因为**它要求的「全序」在高维空间里
不存在**。向量检索放弃精确性、改用图或聚类来近似邻近关系，本质上是在
用「召回率」换「可行性」——这是两个不同问题域的不同解法，不能互相替代。

理解了这一点，也就理解了 RAG 系统为什么要做混合检索：
**关键词检索和向量检索各自守着一种「相似」的定义，谁也替代不了谁。**
