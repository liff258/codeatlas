# 上下文窗口不够用怎么办

> 本文为 CodeAtlas 项目自写素材。许可证：项目原创。
> 关键词：上下文窗口、Context Window、token 预算、长文本、截断

## 先搞清楚"不够用"是什么意思

说上下文不够，通常指三种不同的情况，解法完全不同：

1. **真的超了**：拼出来的 prompt 超过模型上限，请求直接报错。
2. **没超但效果变差**：塞进去了，但模型开始漏掉中间的内容。
3. **没超但成本受不了**：能塞，但每次调用都烧掉几万 token，账单和延迟都难看。

第一种是硬约束，第二种是注意力机制的特性，第三种是工程账。
大部分人抱怨的其实是第二种和第三种，却按第一种去解决（拼命截断），结果越截越差。

## 硬约束：token 上限怎么算

模型的上下文窗口指的是**输入 + 输出**的总 token 数。常见配置：

- 8K：老一代模型，现在只够做短问答
- 32K / 128K：主流区间
- 200K 以上：少数模型支持，但价格和延迟都上去了

算预算时要预留输出空间。一个 128K 的模型，如果想让模型生成 2000 token 的答案，
输入最多只能用 126K。这一点经常被忽略，表现为"明明没超限却报错"。

中文的 token 估算：大约 **1 个汉字 ≈ 1~1.5 token**（取决于分词器）。
英文大约 **1 个单词 ≈ 1.3 token**。所以 10 万汉字的中文文档，大概就是 10~15 万 token，
塞不进 128K 的窗口。

## 中间丢失：塞进去不等于读到了

这是最容易被忽略的一点。

2023 年斯坦福的 "Lost in the Middle" 研究做过一个实验：把关键信息放在长文档的
不同位置，看模型能不能找到。结论是 **U 型曲线**——放在开头和结尾的召回率高，
放在中间的最容易被忽略。

工程含义很直接：

- 重要的指令和约束放在**开头**（system prompt 天然在开头，这是对的）
- 问题本身放在**结尾**（紧贴生成位置，模型注意力最强）
- 中间塞的是参考资料，但**不要把最关键的那条埋在中间**

这也解释了为什么"把 20 个文档全塞进去让模型自己找"效果往往不如
"先检索出 5 个最相关的再塞"。不是模型不行，是位置决定的。

## 省上下文的五种手段

按性价比从高到低排：

### 1. 检索而不是全塞

最有效的一招。10 万字的文档库，每次只取最相关的 5~8 个片段（约 2000 token），
而不是把整个库塞进去。

代价是要有检索能力（向量 + 关键词 + 重排），收益是**上下文占用降一个数量级**，
而且准确率通常更高——因为模型不用在噪声里挑。

### 2. 摘要而不是原文

对话历史越来越长时，不要保留全部原文。做法是：

- 保留最近 N 轮原文（细节最重要）
- 更早的轮次压缩成一段摘要（"用户之前问了 A、B，结论是 C"）

本项目的做法是只带最近 6 条消息，每条截断到 400 字。
追问需要的通常只是"在聊什么"，不需要完整答案。

### 3. 结构化抽取而不是全文

如果只是要模型从文档里抽几个字段，不要给它整篇文档。
先用规则或小模型把候选段落筛出来，只把候选段落给它。

### 4. 分层：小块检索，大块生成

检索用小 chunk（256 token，向量更聚焦），命中后取它的 parent（1024 token）
喂给模型。这样检索精度和上下文完整度都能拿到，代价只是存储翻倍。

比"直接把 chunk 调大"划算得多——chunk 调大后向量会被稀释，检索反而变差。

### 5. 缓存不变的部分

system prompt、few-shot 示例、固定的工具定义，这些每次都一样。
支持 prompt caching 的模型（如 Claude、部分国产模型）可以把这部分缓存起来，
命中缓存的部分按更低价格计费，延迟也更低。

## 真的超了怎么办：截断策略

如果以上都不够，必须截断，那要按"丢什么损失最小"来排：

| 内容 | 能不能丢 | 说明 |
|---|---|---|
| 历史对话 | 可以，压缩成摘要 | 只保留结论和未解决的问题 |
| 低分检索片段 | 可以，直接丢 | 重排分最低的那几条 |
| 代码块 | 谨慎 | 截断代码等于给模型错误信息 |
| 表格 | 谨慎 | 丢了表头，数据行就没意义 |
| 用户当前问题 | **绝对不能** | 丢了它整个请求就没意义 |
| system 约束 | **绝对不能** | 丢了会输出不符合格式的内容 |

**最糟的截断方式是"从头砍"或"从尾砍"**——它会随机砍掉半句话、半个代码块。
正确做法是按语义单元（段落、代码块、表格行）整块丢弃。

## 一个具体的预算模板

假设 32K 窗口，要生成 1000 token 的答案：

```
system prompt      500 token
历史对话（压缩后）  1500 token
检索证据（8 条）    3000 token
用户问题            100 token
─────────────────────────────
输入合计           5100 token
预留输出           1000 token
剩余可用           25900 token   ← 还有很大余量
```

看到这个数字就该意识到：**32K 对绝大多数问答场景是够的**。
真正的问题往往不是窗口小，而是没有做检索、把整个文档库塞了进去。

## 和 RAG 的关系

RAG 的本质就是"用检索解决上下文不够"：与其把知识全塞进 prompt，
不如把知识放在外部，需要时取一小块。

所以"上下文窗口变大"不会让 RAG 消失，只会改变取舍：

- 窗口小的时候，必须精挑细选，重排很重要
- 窗口大的时候，可以多塞几条候选，但**成本和延迟会线性上升**

而且长上下文还有个隐性成本：**每次请求都要重新处理全部输入**。
10 万 token 的输入，即使只问一句话，也要为这 10 万 token 付钱和等延迟。
检索一次只送 3000 token，成本差 30 倍。

这也是为什么工程上普遍认为：**能检索就不要长上下文**。
