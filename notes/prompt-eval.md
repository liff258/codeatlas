# 提示词评估：怎么知道改得更好

「我感觉这版更好」是提示词工程里最危险的一句话。模型输出方差大、任务没有唯一答案，凭感觉调提示词等于随机游走。这篇讲怎么建评估集、怎么用 LLM 当裁判、怎么防止改一处坏一处。

## 怎么判断一个提示词改得更好？

先定义「更好」是什么。三类指标，必须选清楚：

- **可判定的**（抽取准确率、格式合规率、引用是否越界）→ 写断言，自动化跑。
- **半可判定的**（答案是否覆盖要点、是否答非所问）→ 用评分量表 + LLM 裁判，人工抽检。
- **主观的**（语气、可读性）→ 只能人工盲评，且样本量要够。

流程上必须是：**先建评估集 → 再改提示词 → 跑全量 → 对比**。顺序反了就会陷入「改完看着不错，上线发现别的地方坏了」。

对比时要看三件事：

1. 总体指标有没有提升；
2. **分场景**有没有退化（总体持平但某一类问题掉 20%，是最常见的坑）；
3. 延迟和成本有没有变（提示词变长、思维链打开，都会推高这两项）。

一个实用规则：**改动幅度小于评估集噪声的，一律视为没改**。20 条评估集上从 85% 到 90%，很可能只是运气。

## LLM 当裁判靠谱吗？怎么减少偏差？

靠谱程度取决于任务。经验分界线：

- **适合**：成对比较（A 和 B 哪个更好）、按明确量表打分（是否覆盖了这 5 个要点）、判定是否答非所问。
- **不适合**：需要外部事实核查（它不知道真相，只会顺着文本判断）、需要精确计算、需要领域专家判断。

已知的系统性偏差，必须主动抵消：

1. **位置偏差**：倾向选第一个（或最后一个）。解法是**交换顺序跑两次**，只有两次一致才算数。
2. **长度偏差**：倾向给更长的回答更高分。解法是在量表里明确「简洁也是优点」，或对长度做归一。
3. **自我偏好**：倾向给自己（同家族模型）的输出打高分。解法是用不同家族的模型当裁判。
4. **宽松偏差**：分数集中在 4~5 分，区分度低。解法是强制排序（必须选一个更好的），而不是绝对打分。

工程建议：LLM 裁判用于**大规模初筛**，关键结论人工复核。裁判的提示词本身也要版本化——换裁判等于换尺子，历史数据不可比。

## 评估集该怎么建？多少条够用？

三个原则：

**1. 从真实问题里来，不要自己编。** 自己编的问题会不自觉地避开难点。真实日志里的提问分布、措辞习惯、错别字，都是编不出来的。

**2. 分层，不要只堆总量。** 按维度切分：学科、问题类型（是什么/为什么/怎么做/对比）、难度、是否多跳。每层至少 5~10 条，否则单层指标没有意义。

**3. 标注要能验证。** 每条样本必须写明「答案在哪个文档的哪个片段」。这样检索和生成可以分开评：检索看有没有召回，生成看有没有用对。

数量上：

- **20~50 条**能发现大问题（方向性错误），发现不了小退化。
- **100~200 条**是多数项目的稳态，能支撑 A/B 对比。
- 再多就要考虑自动化生成 + 人工校验，边际收益下降。

比数量更重要的是**稳定性**：同一份评估集，同一套参数，跑两次结果应该一致（生成部分有随机性，检索部分必须完全一致）。不一致说明评估流程本身有问题。

## 为什么不能只看一两个例子的效果？

三个原因，每个都能单独让判断出错：

**1. 方差**。温度 >0 时同一输入的输出分布很宽。一两个例子可能刚好落在好的一侧。

**2. 幸存者偏差**。你挑来看的例子，往往是你最关心的那类问题——而线上分布里它可能只占 5%。

**3. 隐性退化**。提示词改动的影响是全局的：为了让「对比类问题」答得更好而加的规则，可能让「事实类问题」开始编造。只看对比类的例子，永远发现不了。

一个真实的教训模式：为了提升某个指标加了三条强约束，指标确实涨了 3 个点，但另一类问题的拒答率从 5% 涨到 30%——因为约束之间冲突，模型选择了保守。这种问题只有跑全量评估集才会暴露。

## 提示词改了之后，怎么防止旧场景退化？

需要三样东西，缺一不可：

**1. 回归集（regression set）**：把历史上出过问题的 case 固化下来，每次改动都跑。这些 case 是「用真金白银换来的」，比新写的样本值钱。

**2. 版本化**：提示词进代码仓库，每次改动带 commit message 说明「为什么改、预期影响什么」。改坏了能回滚，能对比。

**3. 灰度与监控**：上线先小流量，盯三个指标——格式失败率、拒答率、平均输出长度。这三个是最灵敏的先行指标，比准确率更早报警。

一个具体做法：把提示词的关键约束写成**可断言的形式**，用测试用例覆盖。比如「引用编号必须在 1..n 之间」「输出必须是合法 JSON」「答案必须包含来源文档名」——这些不需要人看，跑测试就能发现退化。

最后一条经验：**提示词的复杂度会单调增长，除非你主动删。** 每隔一段时间做一次「删规则」的实验：去掉某条规则，跑评估集，如果指标没掉，就永久删掉。大部分项目的提示词里都躺着十几条没人知道为什么存在的规则。
