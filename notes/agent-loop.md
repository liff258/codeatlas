# Agent 循环：为什么「自评-改写」比「一次检索」更靠谱

> 本文为 CodeAtlas 项目自写素材。许可证：项目原创。

## 一次检索的问题在哪

最简单的 RAG 是「检索一次，把结果全塞给模型」。它有两个隐含假设：

1. 第一次检索就能召回足够的证据
2. 模型能自己判断证据够不够

两个假设在实践中都经常不成立。

**第一个假设不成立**，是因为用户的问题往往和文档的表述不一致。
用户问「RAG 召回率怎么提」，文档里写的是「混合检索与重排」。
字面不重合，向量也未必能跨过这个语义鸿沟。

**第二个假设不成立**，是因为模型有「幻觉倾向」——证据不足时，
它倾向于用常识补全，而不是承认「我不知道」。

## 拆成显式的几步

把「一次检索」拆成有明确判断点的循环：

```
路由 → 规划 → 检索 → 自评 → (不够) → 改写 → 再检索 → 自评 → 生成
```

每一步都对应一个可以被观察、被记录的状态。这样做有三个好处：

### 1. 错误可以被定位

如果最终答案错了，可以回溯：是路由判断错了领域？规划拆错了子查询？
检索没召回？还是自评阈值太松导致提前生成？

一次性的黑盒 RAG 做不到这一点——你只知道结果不对，不知道为什么。

### 2. 自评是一个可量化的决策点

「证据够不够」不能靠模型说「我觉得够了」，要有一个可计算的指标。

本项目的做法是**覆盖度**：把问题拆成若干子查询，每个子查询对应若干条召回结果，
按分数加权算出「这次检索覆盖了问题的多少」。覆盖度低于阈值（如 0.6）就触发改写。

阈值不是拍脑袋定的，它决定了「宁可多查一轮」还是「宁可早生成」。
阈值低 → 轮数少、延迟低、但容易答不全；阈值高 → 轮数多、延迟高、但证据更充分。

### 3. 改写有明确目标

「改写查询」不是让模型随便换个说法，而是**针对自评发现的缺口**改写：

- 缺术语 → 补充专业术语和中英对照
- 缺对比 → 拆成「A 是什么」「B 是什么」「A 与 B 的区别」三个查询
- 缺具体数据 → 加上限定词（版本号、场景）

有目标的改写，比盲目扩写有效得多。

## 必须有硬约束，否则会死循环

循环结构最大的风险是停不下来。必须设三道上限：

- **最大步数**（如 8 步）：防止节点之间来回跳
- **最大改写轮数**（如 2 轮）：改写两次还不行，说明素材本身缺，继续改写是浪费
- **总超时**（如 60 秒）：防止单次检索卡住拖垮整个请求

这三条不是「优化」，是**正确性要求**。没有它们，一个边界情况就能让服务挂住。

## 降级比失败更重要

检索服务、rerank 服务、LLM 都可能临时不可用。设计上要保证：

- 向量检索挂了 → 降级成纯 BM25，并在日志里记明原因
- rerank 挂了 → 直接用融合后的排名
- LLM 挂了 → 返回已召回的片段，明确告诉用户「未能生成答案，以下是相关原文」

关键是**降级要留痕**。如果向量检索静默失败，排查时会误以为「向量效果不好」，
然后去调一个根本不存在的参数问题——本项目的评测脚本专门打印了降级原因，
就是为了避免这种误判。

## 思考过程为什么要展示给用户

把 Agent 的每一步摊开给用户看，不只是「炫技」，它解决三个实际问题：

1. **建立信任**。用户能看到「系统查了哪些词、找到了什么、为什么觉得不够」，
   对答案的怀疑会少很多。
2. **暴露问题**。用户看到「改写后的查询跑偏了」，可以立刻重新提问，
   而不是对着一个错误答案猜原因。
3. **提供调试信息**。开发阶段，思考面板比日志更好用——它是结构化的、带时序的。

代价是界面复杂度上升。本项目的取舍是：过程放右栏、答案放主栏，
默认都可见，但不打断阅读节奏。
