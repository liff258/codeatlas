# Agent 的记忆怎么设计

> 本文为 CodeAtlas 项目自写素材。许可证：项目原创。
> 关键词：Agent Memory、长期记忆、工作记忆、情景记忆、遗忘机制

## 为什么"记不住"是个真问题

大模型本身是无状态的：每次调用都是全新开始，它不记得上一轮说过什么。
所谓"记忆"，全是应用层自己拼出来的——把历史塞进 prompt，模型看起来就"记得"了。

但这条路很快撞墙：

- 对话长了塞不下（上下文窗口有上限）
- 塞进去也未必读得到（长文本中间的内容容易被忽略）
- 每次都要为全部历史付费，成本线性增长

所以 Agent 的记忆设计，本质上是回答一个问题：
**哪些信息值得留下、以什么形式留、什么时候取出来用。**

## 三种记忆，对应三种时间尺度

借鉴认知科学的分类，工程上通常分三层：

### 工作记忆（Working Memory）

当前这一轮推理需要的临时信息：用户这句话、刚检索到的证据、上一步的工具返回。

- 生命周期：一次请求
- 存储：内存变量 / prompt 本身
- 关键点：**用完就丢**，不要往长期存储里写

### 情景记忆（Episodic Memory）

"发生过什么"：用户上次问了什么、当时的结论是什么、做过哪些操作。

- 生命周期：一个会话，或者跨会话的近期历史
- 存储：对话表（message 表），按 session 分组
- 关键点：存**结论**而不是全文。存"用户在做 RAG 召回率优化，已确认用混合检索"，
  比存 3000 字的完整对话有用得多

### 语义记忆（Semantic Memory）

"这个世界是什么样的"：领域知识、事实、文档内容。

- 生命周期：长期，跨会话
- 存储：向量库 / 知识库
- 关键点：这是 RAG 管的范畴，和对话记忆是两套东西，不要混在一起

**最常见的错误是把三者混成一个"历史消息列表"**。
结果是：临时信息污染长期记忆，检索时把三个月前的寒暄也召回出来。

## 存什么：结论优先

如果只能记一条原则，那就是：**记结论，不记过程**。

对比两种做法：

| 存法 | 内容 | 取出来时 |
|---|---|---|
| 存全文 | 用户问了 A，我说了 B、C、D…… 共 2000 字 | 还要再读一遍才知道结论 |
| 存结论 | 用户在优化 RAG 召回率，已采用混合检索 + 重排 | 一句话就够 |

第二种的好处不只是省 token：

- 检索更准（摘要比长文更容易匹配到关键概念）
- 冲突更容易发现（结论之间可以直接比对，长文之间很难）
- 用户能看懂（"我记得你在做 X"比"你上次说了 2000 字"自然得多）

工程上可以在每轮对话结束时，让模型抽一条结构化摘要落库：
`{主题, 关键结论, 待解决问题}`。成本很低，收益很高。

## 什么时候取出来：检索式记忆

如果记忆量小（几十条），全塞进 prompt 也行。
一旦上百条，就必须检索——**记忆库本身就是一个 RAG 系统**。

做法和文档检索一样：

1. 把每条记忆做成一个向量（存结论的好处在这里体现：短、聚焦）
2. 新问题来时，先用问题检索相关的记忆
3. 只把 top-3~5 条拼进 prompt

这里有个容易忽略的点：**记忆检索和文档检索应该分开做**。
混在一个库里，会出现"用户三个月前问过类似问题"压过"知识库里最权威的那段文档"，
而后者才是回答问题的依据。

## 遗忘机制：不删等于没有

记忆系统最容易做错的地方是只增不删。后果：

- 检索时噪声越来越多，准确率随时间下降
- 存储成本无限增长
- 过时的信息（比如"项目用 MySQL 5.7"）会持续污染回答

三种可行的遗忘策略：

### 1. TTL（生存时间）

按类型设过期时间：临时偏好 7 天，项目背景 90 天，长期事实不过期。
简单粗暴但有效，适合大多数场景。

### 2. 重要性打分

写入时让模型给一个 1~5 的重要性分，低分的定期清理。
分数可以参考：用户是否明确说"记住这个"、信息是否可推断、是否重复出现。

### 3. 冲突消解

新记忆和旧记忆矛盾时（"用 MySQL 5.7" vs "已升级到 8.0"），
不是简单叠加，而是**用新的覆盖旧的**，并把旧的标记为已失效而不是删除——
保留历史有助于回答"什么时候改的"这类问题。

## 一个具体的最小实现

如果不想一上来就做复杂系统，这个结构够用：

```
memory 表
├── id
├── session_id      哪个会话产生的（情景记忆）
├── kind            fact / preference / decision
├── content         一句话结论（不超过 200 字）
├── embedding       向量（用于检索）
├── importance      1~5
├── created_at
└── expires_at      NULL 表示不过期
```

写入时机：每轮对话结束，抽一条摘要。
读取时机：新问题来时，检索 top-5，按 importance 和相似度加权排序。
清理时机：每天跑一次，删掉过期的和低分且长期未被检索到的。

这套东西不到 200 行，但能覆盖 80% 的场景。

## 和上下文窗口的关系

记忆和上下文是同一枚硬币的两面：

- **上下文窗口**是"这一次能看多少"
- **记忆**是"长期能记住多少"

窗口再大也解决不了记忆问题——因为窗口是每次请求独立的，而记忆要跨请求存在。
反过来，记忆做得好，窗口小一点也能用：只取相关的那几条，比全塞进去更准。

所以不要把"模型支持 200K 上下文"当成"不需要做记忆管理"的理由。
200K 的输入每次都要重新计费和处理，而记忆检索只取 3000 token。

## 一句话总结

Agent 的记忆不是"把历史存起来"，而是**在正确的时间，取出正确的那一小段**。
设计重点是三件事：存结论不存过程、检索而不是全塞、该忘的必须忘。
