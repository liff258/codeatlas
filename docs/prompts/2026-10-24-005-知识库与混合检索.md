## 4. AI 的关键输出

AI 先做了一轮**环境侦察**，而不是直接写代码。这一步的价值在事后看非常高：

| 探测 | 结果 | 影响 |

## 5. 我的修正与判断

### 判断 1：素材抓取改用 sparse checkout

AI 一开始选了 codeload 下 tarball，下了 77 秒才 1.5MB，整包可能有几十 MB。
我让它换成：

```bash
git clone --depth 1 --filter=blob:none --sparse
git sparse-checkout set --no-cone 'docs/java/basis/*.md' ...
```

**28 秒拿到 74 个 md**，快了一个数量级。后面补集合框架目录时网络又断了，
再改用 GitHub Contents API 拿 base64，12 个文件一次搞定。

> 这件事的通用教训：抓 GitHub 上的特定目录，永远优先 sparse checkout，
> 不要下整包。

### 判断 2：切片不能让代码块和表格被切碎

AI 第一版把「超长代码块整块保留」写死了，结果有个 1701 token 的 SQL 笔记
独占一个 chunk——远超 256 预算，向量会被彻底稀释。

我要求改成：**超长代码块按空行切成逻辑段，每段补回 ``` 围栏**；
**超长表格按行切，每段重复表头**。

改完之后 max 从 1701 降到 629，且每一段单独拿出来仍然是合法可读的代码/表格。
剩下 8.5% 超预算的都是单个代码块，这是刻意保留的——语义完整比长度均匀重要。

### 判断 3（最重要）：manifest 的素材目录指错了

做检索基线时发现「HashMap 的扩容机制」这条查询效果很差，top-3 全是
ThreadLocalMap 和缓存分类。AI 一开始准备去调 BM25 参数。

我让它先查库确认：

```sql
select count(*) from chunk where content ilike '%负载因子%'  -- 0
```

**库里根本没有 HashMap 扩容的内容。** manifest 把集合框架（HashMap/ArrayList）
的 covers 写在 `jg-java-basis` 名下，但那些文章实际在 `docs/java/collection`。

补了 12 篇之后，child chunk 从 4772 涨到 5219，那条查询的 top-2/top-3 立刻变成
HashMap 相关内容。

> 这是这一轮最有价值的一次排查。如果当时直接去调 BM25 的 k1/b 参数，
> 会调到一个**根本不存在的问题**上——素材缺口伪装成了算法问题。

### 判断 4：分词是 BM25 的命门，必须自己喂词典

两个坑，都是静默失败：

1. jieba 默认词典不认识「红黑树」，在「为什么比红黑树快」里切成「比红」+「黑树快」。
   → 补了 `app/rag/dict.txt`，约 150 个计算机术语，词频给 1000。
2. 「B+树」会被技术词正则先切成「b+」，jieba 根本没机会看到完整词。
   而 **B+树 vs B树** 恰恰是 MySQL 索引最经典的一组对比，分不出来就等于没做。
   → 允许技术词后接一个中文名词（树/表/锁/池/队列/缓存），
   并先把「B+ 树」这种带空格的写法归一成「b+树」。

验证：

```
B+树和B树的区别  ->  b+树 / b树 / 区别   ✓
为什么比红黑树快  ->  什么 / 为什么 / 红黑树  ✓
```

### 判断 5：RRF 而不是加权分数

BM25 分数是无界的（实测 10~50），余弦距离是 0~2，量纲完全不同。
想加权就得归一化，而归一化本身要拍参数。

RRF 只看排名不看分数：`score(d) = Σ 1/(k + rank)`，k=60 是经验值。
零参数、对量纲免疫、一路挂了另一路还能用。这不是最优解，但是最不容易出错的解。

## 6. 踩到的工程坑（都是真的，不是编的）

| 坑 | 现象 | 原因 |
|---|---|---|
| `:vec::vector` | `syntax error at or near ":"` | SQLAlchemy 的 `:name` 绑定与 PostgreSQL 的 `::` 类型转换冲突，必须写 `CAST(:vec AS vector)` |
| batch=128 + max_len=512 | 3 分钟一条都没提交 | 单批 65536 token，CPU 上跑不动。实测甜点区是 batch=16 / max_len=384 |
| torch 线程限 4 | 吞吐只有一半 | 16 核机器，默认 8 线程，我限到 4 是白白浪费 |
| `model_cache_dir` 是 str | `TypeError: unsupported operand for /` | pydantic 的 str 字段要和 Path 拼，得显式转 |
| Docker 停了 | `ConnectionTimeout` | 隔天开机 Docker Desktop 没自启，`docker desktop start` 拉起来 |
| git push 502 | `CONNECT tunnel failed` | 环境变量里有失效代理，curl 加了 `--noproxy` 但 git 没绕过 |

## 7. 这一轮之后的状态

| 项 | 数字 |
|---|---|
| 文档 | 131 篇 |
| parent chunk | 853 |
| child chunk | 5219 |
| 向量 | 1024 维，bge-m3 本地推理 |
| 单测 | Python 44 个（14 SSE + 15 切片分词 + 8 RRF + 7 embedding） |

**评测结果**（20 题：15 关键词 + 5 语义，候选池 5219）：

| 模式 | 关键词 Hit@1 | 关键词 Recall@5 | 语义 Recall@5 | 总体 Recall@5 |
|---|---|---|---|---|
| BM25 | **60.0%** | 93.3% | 40.0% | 80.0% |
| 向量 | 33.3% | 73.3% | 80.0% | 75.0% |
| 混合 | 46.7% | 93.3% | **80.0%** | **90.0%** |

**三个结论**：

1. BM25 在关键词题上碾压（60% vs 33%）。问「SATB」「AQS」这种罕见缩写，
   精确词命中就是最强信号。
2. 向量是唯一在语义题上能打的。问「多个线程同时改一个数怎么保证不出错」，
   BM25 召回读写锁（词面相近但不对），向量召回 CAS 乐观锁（正确答案）。
3. 混合的价值在**召回率**不在第一名：90% 总体 Recall@5 三者最高。
   对 RAG 来说这才是关键指标——后面还有 LLM 在筛，正确答案只要在候选里就行。

**两个失败的调参尝试（记下来避免以后重走）**：

- RRF 的 k 从 1 试到 60，Hit@1 最好也只有 46.7%，调不动。
- 想用「BM25 分数门控」把语义题里的噪声滤掉：实测关键词题 10.05~43.69 分、
  语义题 15.04~19.69 分，**分布完全重叠**，没有可分的阈值。
  gate=12 能到 40% 但那是过拟合 20 条样本。

→ 结论：Hit@1 的问题**不是融合策略能解的**，必须靠 reranker。这是 P1-c。
