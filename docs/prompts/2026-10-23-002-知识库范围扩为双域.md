# Prompt #002 · 知识库范围从「Java 八股」扩展为「后端 + AI 双域」

- **日期**：2026-10-23
- **工具**：WorkBuddy AI（DeepSeek-V4.1-Flash）
- **阶段**：P0 骨架
- **关联提交**：`feat(contracts): 学科分类体系与跨域边`

---

## 1. 目标

把知识库范围从「Java 后端八股」调整为「后端知识 + AI 相关知识」，并评估这个调整对架构、契约、演示主线的影响。

## 2. 上下文

第一版方案（Prompt #001）定的是纯 Java 后端八股：JVM / 并发 / MySQL / Redis / Spring。理由是"贴合求职、痛点真实、素材好找"。

用户提出：「计算机知识库主要后端知识与 ai 相关知识」。

## 3. 我的 Prompt

> 计算机知识库主要后端知识与ai相关知识

（极短的一句需求变更。没有说"怎么改"，只说了"是什么"。）

## 4. AI 的关键输出

AI 没有停留在"改一下文档范围"，而是指出这个调整会**改变产品的核心差异化**：

1. **双域让「跨域边」成立**。原本纯 JVM 的知识库，图谱只是同一学科内的关系网，和向量检索的差距不明显。加了 AI 域之后，「向量检索 ↔ B+ 树」这类跨域关系成为可能——而向量检索按语义相似度召回，**召不回"关系"本身**。
2. **演示主线必须换**。原主线「G1 的 SATB 为什么要配写屏障」是单域深度问题，体现不出跨域价值。新主线换成「向量检索为什么不能用 B+ 树加速？那 RAG 的召回率该怎么提？」，一个问题横跨两个域，4 跳。
3. **学科枚举不能硬编码**。双域之后学科从 5 个变成 14 个，如果 Java / Python / 前端各写一份枚举，改一次要动三处。应该建 `subject_taxonomy` 表作为唯一真相。
4. **工期风险**：素材量从 8–12 篇涨到 12–15 篇，但**不能等比例涨**——AI 域只挑 5 篇最关键的（HNSW 论文、RAG 论文、Anthropic Agent 博客、Prompt Guide、LLM 基础），不追求全覆盖。

## 5. 我的修正与判断

| AI 的建议 | 我做了什么 | 为什么 |
|---|---|---|
| 建 `subject_taxonomy` 表 | **采纳**，并加 `domain` 和 `color` 两个字段 | `domain` 用来判断跨域边，`color` 直接驱动前端配色，省掉一份前后端共享的颜色常量 |
| 演示主线换成跨域问题 | **采纳，但保留原 JVM 问题做第二问** | 只留跨域问题会显得"广而浅"。先证明广度，再证明深度，节奏更好 |
| AI 域只挑 5 篇 | **采纳** | 12–15 篇里 AI 占 5 篇，比例约 1:2.4，够撑起跨域演示，又不至于拖垮建库 |
| 没提的一个点 | **我补的**：跨域边数量做成硬指标（≥30 条） | 如果只喊"支持跨域"，最后建出来 3 条跨域边，演示时画不出那条虚线，卖点就塌了。必须可量化验收 |
| 没提的一个点 | **我补的**：把 `subject` 从字符串枚举改成外键 | 原来 `chunk.subject` 是裸 VARCHAR，打标 Agent 完全可能打出「RAG检索」这种不在枚举里的值。外键直接让脏数据写不进去 |

**一个反直觉的判断**：AI 建议把「后端 8 篇 / AI 5 篇」写进 README 当作产品说明。我没有采纳——对外不该暴露"我们只有 5 篇 AI 资料"，这个比例是内部排期约束，不是产品卖点。
