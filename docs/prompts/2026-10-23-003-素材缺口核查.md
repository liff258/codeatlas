## 1. 目标

在动手建库之前，验证「后端 8 篇 + AI 5 篇」这个素材规模是否真的能支撑演示主线和 50 题评测集。

## 2. 上下文

Prompt #002 把知识库扩成双域后，素材量定在 12–15 篇。这个数字是拍脑袋估的，没有对着演示主线反推过。

## 3. 我的 Prompt

> 素材够吗

## 4. AI 的关键输出

AI 没有直接回答"够"或"不够"，而是先做了一件事：**拿演示主线的每一跳去反查素材覆盖**。结果发现三个硬缺口：

**缺口一：跨域边不会自己长出来（最致命）**
三元组抽取是从单个 chunk 里抽的。HNSW 论文里不会提到 B+ 树，MySQL 笔记里不会提到 HNSW。所以跨域边不能指望自动抽取，必须专门做一步「图谱补全」：先用实体描述向量粗筛候选对，再让 LLM 逐对判定关系。

**缺口二：主线问题的答案，现有素材答不全**
「向量检索为什么不能用 B+ 树加速」——标准八股只讲 B+ 树**适合**什么（等值、范围查询），从不讲它**不适合**什么（高维向量）。这个对比知识几乎没人在单篇文档里写过。必须自己写一篇。

**缺口三：AI 域 5 篇偏论文，不够用**
论文语言密度高但抽象。学生真实学习看的是中文解读和工程实践文档。

**另外查出一个版权问题**：CS-Notes 的许可证实际是 **CC BY-NC-SA 4.0**（含不可商用 + 相同方式共享），不是我之前写的 CC BY-SA。JavaGuide 是 Apache-2.0，干净。

## 5. 我的修正与判断

| AI 的建议 | 我做了什么 | 为什么 |
|---|---|---|
| 扩到 23 篇 | **采纳**：后端 11 + AI 8 + 自写 4 | 3950 chunk，pgvector 毫无压力。建库是自动的，人工成本只在选源和写 4 篇笔记 |
| 做图谱补全脚本 | **采纳，并加了 `inferred_by` 字段** | 推断出来的边要能溯源。前端对 `inferred` 的边用更低透明度，诚实展示"这是推断的"，而不是假装和抽取的边一样可靠 |
| 写《向量检索 vs B+ 树》 | **采纳，标为全项目最高优先级** | 只有 60 个 chunk，但它决定主线问题能不能答完整。没有它，整个演示的差异化卖点就是空的 |
| 弃用 CS-Notes | **采纳，并在 README 写明原因** | 许可证冲突不该藏着。主动写出来反而是加分项——说明作者认真核过版权 |
| AI 建议"只对 Apache/MIT 的源全文入库，其余只存自写摘录" | **采纳，写进 manifest 的 license_policy** | 这条策略一石二鸟：规避版权风险，同时让知识库内容本身构成原创，符合"作品须为原创"的要求 |

**一个我自己加的判断**：AI 把素材清单列成了"书单"，但书单不能直接喂给建库脚本。我把它落成了机器可读的 `sources.manifest.yaml`，每篇带 `fetch_mode`（fulltext/excerpt/summary）、`license`、`expected_chunks`、`covers`。这样建库脚本可以按清单自动抓取，也能直接统计"每个学科多少 chunk"——**验收指标从口头承诺变成了可执行检查**。
