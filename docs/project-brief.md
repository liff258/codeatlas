# CodeAtlas · 项目说明书

> 面向后端与 AI 学习的知识平台：**把线性的文档，还原成网状的知识。**
>
> 一句话区分：普通 RAG 回答「这段话说的是什么」，这个系统回答「这件事和那件事是什么关系」。

---

## 一、问题：准备面试的人不缺资料，缺三件事

| 缺口           | 现状                    | 后果                                             |
| ------------ | --------------------- | ---------------------------------------------- |
| **不知道学什么**   | 收藏了 30 篇面经、5 个仓库，打开就懵 | 从「最简单的一篇」开始，学了两周还在 Java 基础                     |
| **不知道学到哪**   | 没有进度、没有边界感            | 反复看同一批内容，或者漏掉整块（比如 JVM 调优）                     |
| **不知道知识的关系** | 文档是线性的，一页接一页<br />    | 记住了「AQS 是队列同步器」，但不知道它和「CAS」「volatile 内存语义」怎么咬合 |

**关键判断：这三件事，聊天框解决不了。**

聊天框的前提是「你知道自己要问什么」。而学习场景里，用户往往正是不知道该问什么的人。  
一个只等着被提问的系统，既不督促也不引导——这是本项目最初的形态，也是被推翻的形态。

---

## 二、产品形态：先给结构，再给追问的出口

```
首页（15 个板块，14 个有内容）
  └─ 学科页（全部知识点 / 面试题，两个 tab）
       └─ 知识点详情（正文 + 涉及概念 + 相关推荐 + 前后篇）
            └─ 点概念 → 实体页（关系网，节点可继续跳）
                 └─ 任意页面右下角「助手」→ 独立会话追问
对话页：独立入口，保留完整问答能力（不再是首屏）
```

**为什么是「三层钻取」而不是「学习路径」**：路径需要人工定义顺序，14 个学科 × 平均 150 个知识点，  
排一遍就是几千条人工决策，三周内做不完，而且排错了比不排更糟。三层钻取是结构化的最小可用形态，  
顺序交给「相关推荐 + 前后篇」这种局部信号去引导。

**agent 的位置**：从入口降级成辅助。逛的时候不需要它，卡住的时候它才出现。

## 三、技术方案

### 3.1 分层架构

```
浏览器（React 18 + TS + Vite + Tailwind + zustand）
   ↓  /api/*
Java 网关（Spring Boot 3 · 端口 8080）—— 唯一对外入口、契约守门、SSE 转发
   ↓  /internal/*（X-Internal-Token）
Python Agent（FastAPI · 端口 8000）—— 编排、检索、生成
   ↓
PostgreSQL 16 + pgvector（端口 5433）
```

**为什么要有 Java 网关**：对外只暴露一个入口，契约（`contracts/openapi.yaml`，20 个端点）  
在这一层收口；Python 侧只认内部 token，不直接对外。代价是多一跳，收益是前端不需要知道  
后端有几个服务。

### 3.2 检索：四模式对比后选型，不是拍脑袋

同一套 37 道题（29 道关键词题 + 8 道语义题，后端 20 / AI 17，候选池 5667）：

| 模式          | Hit@1     | Recall@5  | 后端 R@5 | AI R@5   |
| ----------- | --------- | --------- | ------ | -------- |
| BM25        | 51.4%     | 81.1%     | 85.0%  | 76.5%    |
| 向量（bge-m3）  | 43.2%     | 81.1%     | 80.0%  | 82.4%    |
| 混合（RRF）     | 51.4%     | 91.9%     | 95.0%  | 88.2%    |
| **混合 + 重排** | **78.4%** | **94.6%** | 90.0%  | **100%** |

三个从数据里读出来的结论：

1. **BM25 在罕见缩写上不可替代**。问「SATB」「AQS」，精确词命中就是最强信号，  
   向量反而被「G1 收集器」这类高频主题词带偏。
2. **混合的价值在召回，不在首位**。RRF 只看排名，BM25 那个又准又强的第一名会被向量中段稀释——  
   调 k（1/3/5/10/20/60 全试过）、用分数门控（关键词题 10~~44 分、语义题 15~~20 分，分布完全重叠）都修不了。  
   **只能靠重排把首位拉回来**（51.4% → 78.4%）。
3. **语义题是短板**（重排后 Hit@1 62.5%）。口语化提问和章节标题之间的措辞差距，  
   重排补不回来——需要 query 改写，不是调参能解决的。

> **一个被数据推翻的结论**：上一版 33 题时，AI 域 BM25 明显落后向量（46.2% vs 61.5%），  
> 我归因成「AI 素材是英文的」。补了两篇中文笔记后，BM25 反超（58.8% vs 52.9%）。  
> 归因是对的，但**结论说反了**：BM25 的劣势来自跨语言，不是来自「AI 领域」本身。  
> 数据推翻自己的结论时，改结论，不是改数据。

### 3.3 知识图谱：离线抽取 + 两道防幻觉校验

**做法**：每篇文档调一次模型抽概念和关系（145 次调用），不是每个 chunk 调一次（5484 次，约 4.5 小时）。

**先试过一个更省事的方案，放弃了**：直接用章节标题当概念。抽出来全是  
「完整代码以及测试」「按准备时间安排复习」「参考」——这种节点比没有图更糟，评委一眼看出是噪声。

**两道防幻觉校验**：

- 概念必须在正文里真实出现（归一化后子串匹配）
- 边的两端必须都在保留下来的概念里

模型编的词直接丢掉。**跨域边不是模型说的**：实体学科归属按全库 chunk 众数统计，  
两端 domain 不同才算跨域——模型输出里根本没有这个字段。

**产出**：727 个概念 / 538 条关系 / **16 条跨域**。

### 3.4 知识点：从 chunk 派生成表，而不是查询时现算

`knowledge_point` 表由 Python 写、Java 只读（符合项目的表所有权不变量）。

**为什么必须落表**：

1. 前端要稳定 id 做 URL（`#/kp/kp_10641b8fa9d3`），现算的 hash 反查不回来
2. 一道题的答案常跨 2~3 个 child chunk，必须按 `heading_path` 聚合、按 `ordinal` 拼接
3. 题库要按 `is_question` 筛，这个标记得预先算好并建索引

**最关键的一条：只用 child 聚合，绝不用 parent 当答案。**  
parent chunk 是 1024 token 滑窗，903 个里有 787 个跨多个 `heading_path`，  
拿它当答案会把上一道题的尾巴拼进下一道题。

**自检也踩过坑**：第一版用「正文里出现别的知识点标题两次以上就算串题」，跑出 10 条报警，  
**全是误报**——「StampedLock 的性能为什么更好？」正文里当然会两次提到 StampedLock，  
而 StampedLock 本身也是另一个知识点的标题。文本启发式区分不了「引用」和「串题」。  
改成结构校验：验证同一条知识点的所有 chunk 属于同一个 `heading_path`，不通过直接非 0 退出。

### 3.5 可溯源：编号由代码分配，模型只能引用已存在的编号

答案里的 `[1]` `[2]` 不是模型自由发挥：编号在拼 prompt 时由代码分配，  
模型引用越界编号时保留正文但标「无出处」。前端每个角标可点开看原文片段。

**这是「能不能被追问」的分界线**：评委问「这句话哪来的」，能当场点开。

### 3.6 降级：每一层都假设下一层会挂

| 层         | 挂了会怎样 | 现在怎么处理                                                                 |
| --------- | ----- | ---------------------------------------------------------------------- |
| 模型超时      | 整轮卡住  | 每节点独立超时（router 10s / planner 15s / grader 12s / rewriter 12s），超时用兜底值继续 |
| 模型限流（429） | 直接失败  | 内部重试 2 次，仍失败则降级并在界面上标黄                                                 |
| JSON 解析失败 | 答案乱码  | 四级容错：剥 \`\`\` 围栏 → 括号配对扫描 → 修尾逗号/中文引号 → 用栈修括号失衡；救不回来老实返回 None 走降级      |
| 检索无结果     | 编答案   | 覆盖率低于阈值 → 先改写重查（最多 2 轮）；仍不足则提示词要求开头写明「现有资料不足以完整回答」                     |

**界面上看得见降级**：思考面板逐节点显示耗时、状态、降级原因。  
不是「转圈圈然后出结果」，而是「你能看到它在干什么、哪里退让了」。

## 四、实测数据

| 项   | 数值                                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------- |
| 语料  | 159 篇文档 / 932 parent chunk / **5,667 child chunk**（全部有向量）                                                         |
| 学科  | 15 个（后端 9 / AI 5 / 通用 1），**14 个有内容**                                                                              |
| 知识点 | **2,167 个**                                                                                                       |
| 面试题 | **840 道**（Java基础 158 / 网络 134 / 并发 128 / Redis 83 / Spring 58 / MySQL 56 / MQ 56 / 分布式 39 / JVM 29 / **AI 域 99**） |
| 图谱  | 727 概念 / 538 关系 / **16 条跨域**                                                                                      |
| 检索  | 37 题：Hit@1 78.4% / Recall@5 94.6%                                                                                 |
| 响应  | 热态 **13.3s**（优化前 31.0s，−57%）；冷启动首个问题不再额外等 40~60s（模型改为启动时预热）                                                       |
| 测试  | **153 个**（Python 98 / Java 42 / 前端 13），全绿                                                                         |
| 代码  | **14,963 行**（Python 4,570 / Java 2,547 / 前端 4,556 / 脚本 3,290）                                                     |
| 接口  | 契约 20 个，实现 **18 个**（2 个写清不做的理由）                                                                                   |

### 响应优化：5 次模型调用里砍掉 2 次

| 阶段        | 优化前       | 优化后       | 做法                                     |
| --------- | --------- | --------- | -------------------------------------- |
| router    | 0.8s      | **0.0s**  | 关键词规则替代模型（输出只有 5 个枚举值）                 |
| planner   | 2.1s      | 4.5s      | 未改（模型波动）                               |
| retriever | 4.5s      | 4.1s      | 未改                                     |
| grader    | **12.0s** | **0.0s**  | 证据 ≥6 条且前 3 条重排分均值 ≥0.75 → 直接判 proceed |
| generator | 11.6s     | **4.7s**  | 证据 12→6 条，输入 token −41%                |
| **合计**    | **31.0s** | **13.3s** | **−57%**                               |

**基线里 grader 等了 12 秒超时，最后用的还是兜底值**——这 12 秒完全白等。  
判断依据不是「感觉可以省」：grader 的任务是判断「证据够不够」，而重排分本身就是  
「这条证据有多相关」，前三条都 ≥0.75 时结论必然是 proceed。

**三个刻意的保守设计**：

- chitchat 只在 ≤12 字的短问题里判（「你好，请问 AQS 是什么」必须走检索，判错代价最大）
- grader 的覆盖率必须标「跳过模型自评」，不能让启发式数字看起来像模型判断
- 弱证据仍然走模型——那才是真正需要判断要不要改写的场景

## 五、创新点（三条，都能被验证）

1. **知识点是派生表，且有结构自检**  
   不是「把 chunk 拼起来」就完事。自检断言「同一知识点的所有 chunk 属于同一 heading_path」，  
   不通过直接非 0 退出——**宁可构建失败，也不把串了题的答案写进库**。
2. **跨域边由代码算，不由模型说**  
   实体学科归属按全库 chunk 众数统计，两端 domain 不同才算跨域。  
   模型输出里没有这个字段，所以「这条线是编的」这个质疑不成立。  
   三处（请求时图谱 / 全库图谱 / 实体详情）共用 `DomainRule`，避免一处写错出现假边。
3. **降级是看得见的**  
   每个节点独立超时 + 兜底，思考面板逐节点显示耗时和降级原因。  
   演示时如果撞上限流，可以当场解释「这就是降级」，而不是尴尬地等。

## 六、不足与下一步（主动说，比被问出来好）

| 不足                  | 现状                                                    | 为什么现在不补                                |
| ------------------- | ----------------------------------------------------- | -------------------------------------- |
| **AI 域资料少**         | 只有 22 道题，其中 Agent 6 道，LLM基础/RAG/向量检索/Prompt工程 合计 16 道 | 语料只占 5% 且多为英文论文，标题不是问句。标「建设中」，不拿别的学科凑数 |
| **题目是启发式抽的**        | 标题含问句词 + 正文 ≥100 字 → 当成一道题                            | 人工筛 840 道不现实。列表标「自动抽取·附原文」，点开能验证       |
| **语义题 Hit@1 62.5%** | 口语化提问和章节标题措辞差距大                                       | 需要 query 改写（用模型把口语转成术语），是独立一块工作        |
| **没有学习进度**          | 只有相关推荐 + 前后篇                                          | 做进度就要有用户体系，三周内会把主线拖垮                   |
| **文件上传未实现**         | `POST /api/documents` 契约有、实现标 ❌                       | 上传后的解析/切片/向量化是一条独立链路，半做不如不做            |
| **无鉴权、无 CI**        | 演示环境够用                                                | 本地跑得通，但没有自动化门禁——这是最该补的工程债              |

**下一步优先级**（按性价比排）：

1. 补 AI 域中文素材（评测已证明：素材覆盖度比调参重要得多）
2. query 改写（针对语义题短板）
3. 题库按难度分层（`difficulty` 字段现在是全 NULL）
4. CI 门禁

## 七、可复现性

```bash
# 1. 起环境（数据库 → Agent → 网关 → 前端，逐级等健康检查）
python scripts/dev_up.py --preheat

# 2. 重建知识点（约 20 秒，纯 SQL 聚合，不调模型）
python scripts/build_knowledge_points.py

# 3. 重建全库图谱（抽取结果已缓存在 data/graph/，--load-only 秒级）
python scripts/build_graph.py --load-only

# 4. 跑检索评测（37 题四模式）
python scripts/eval_retrieval.py --mode rerank

# 5. 端到端验证（逐节点耗时 + 契约断言）
python scripts/e2e_verify.py --strict-cross-domain
```

**抽取结果（436KB）和知识点构建脚本都已提交**，clone 下来不用重新调模型就能复现图谱。  
`docs/demo-script.md` 是 6:20 演示分镜，含 7 种意外情况应对和评委可能问的 10 个问题。
